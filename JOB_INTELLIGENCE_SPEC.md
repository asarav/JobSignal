## 1. Product vision and scope

### 1.1 Vision

Build a lightweight, local-first desktop application that helps people **discover, evaluate, prioritize, and manage** job opportunities across the internet, replacing the functionality of Simplify Copilot while being faster, more reliable, more transparent, and more extensible.

**Central goal:** *Help users spend their time applying to legitimate, relevant opportunities rather than repeatedly encountering duplicates, stale postings, or jobs that may not lead anywhere.*

The application prioritizes **actionable opportunities over volume**. A smaller list of trustworthy, relevant, non-duplicate jobs is better than a large noisy one.

### 1.2 Capabilities (functional scope)

1. Discover job postings from ATS boards, employer career pages, user-supplied URLs/companies, local employer lists, and optional search-engine discovery.
2. Crawl employer career pages and supported ATS platforms responsibly.
3. Extract and normalize job information into a canonical model, preserving partial data and provenance.
4. Filter by configurable user preferences (hard filters) separate from ranking.
5. Parse locally stored resumes (PDF, DOCX, TXT) into a normalized candidate profile.
6. Evaluate candidate–job compatibility.
7. Rank opportunities with explainable multi-objective scoring.
8. Detect duplicates and reposts.
9. Assess posting credibility (stale / inactive / potential ghost postings) with explainable evidence, keeping **risk** and **confidence** separate.
10. Track companies and application history; apply configurable cooldown-based suppression.
11. Autofill application forms **without ever submitting them**.
12. Surface frequently requested skills missing from the resume.
13. Maintain history that improves recommendations over time (outcome feedback).
14. Operate locally with no account, no cloud infrastructure, and no paid API keys.

### 1.3 Non-goals (MVP)

- No hosted backend, user accounts, sync service, or telemetry.
- No automatic application submission, ever (not a configurable option).
- No bypassing of authentication, CAPTCHAs, bot protection, or robots rules.
- No resume rewriting or fabricating of experience.
- No third-party plugin marketplace (internal modularity only; see §4.6).
- No requirement for an LLM. Optional local models are allowed behind `ModelProvider`.
- No scraping of sites whose terms or robots directives disallow it; no scraping of LinkedIn/Indeed-style login-walled sources.
- No claim that any score is a probability of interview or offer.

### 1.4 Primary persona

A technical or non-technical job seeker applying to dozens or hundreds of roles over weeks or months, who wants to avoid re-applying to the same role, wants to know which postings are likely dead, and wants to understand which missing skills matter. They use one desktop machine (Windows, macOS, or Linux).

### 1.5 Glossary

| Term | Meaning |
|---|---|
| **Posting** | One observed listing at a specific URL/source ID. |
| **Job** | The canonical internal entity representing one real-world position; may have many postings (aliases). |
| **Alias** | A (source, source_posting_id, URL) triple attached to a job. |
| **Snapshot** | Immutable captured version of a job's extracted content at a point in time. |
| **Observation** | A timestamped fact about a job (seen on crawl, endpoint check, etc.). |
| **Signal** | A normalized output from a `PostingSignalProvider` (risk contribution + confidence + evidence). |
| **Risk** | Estimated likelihood that a posting does not represent active hiring (`0..1`). Heuristic, not a probability. |
| **Confidence** | How much evidence supports the risk estimate (`0..1`). Independent of risk. |
| **Hard filter** | A user-defined constraint that excludes a job before ranking. |
| **Cooldown** | Period after an actual application during which similar roles are suppressed. |
| **Connector** | A `JobSourceConnector` for a specific ATS/source type. |
| **Strategy** | An `ExtractionStrategy` that turns a URL/response into job data. |

## 2. Core principles (and what they mean in code)

Every architectural decision MUST be consistent with these principles. Each has an enforceable consequence.

| # | Principle | Enforceable consequence |
|---|---|---|
| 2.1 | **Local-first** | All user data lives in the app data directory. No network call carries user data (resume text, profile, history). Outbound traffic is limited to fetching public job pages. A CI test asserts the worker makes no outbound request during resume/matching/application flows (network-denied test mode). Optional external services (e.g. search-engine discovery) are off by default, individually enabled, and disclosed in Settings with the exact data sent. |
| 2.2 | **Lightweight** | Idle CPU ≈ 0; idle RSS budget in §17. Heavy work runs in background tasks with bounded concurrency. Optional heavy deps (ONNX, Playwright browsers) are lazily loaded and optional at install. |
| 2.3 | **Modular and replaceable** | Domain depends only on ports. Swapability tests (§4.8) run in CI. |
| 2.4 | **Explainable** | Every score, suppression, deprioritization, and risk assessment is persisted with machine-readable *reasons* and *evidence* and rendered in the UI. There is no code path that returns a bare number. |
| 2.5 | **Graceful degradation** | Per-call isolation, timeouts, and circuit breakers around plugins. Partial extraction results are persisted with `extraction_status='partial'`. Failure of one source never fails a crawl run for others. |
| 2.6 | **User control** | The app recommends, filters, ranks, and autofills. It never submits. Every suppression is reversible. Every automated judgment can be overridden by the user. |
| 2.7 | **Missing ≠ negative** | Absent data yields *missing* signals (excluded from aggregation), never negative evidence. |
| 2.8 | **History is append-only** | Observations, snapshots, signals, assessments, and events are never overwritten or deleted by normal operation. "Current" values are derived or stored as pointers to the latest immutable record. |
| 2.9 | **Cautious language** | UI/IPC copy about employers and postings uses hedged phrasing (e.g. "Repeated reposting observed"), never accusations. A lint test scans UI strings for banned phrases (e.g. "scam", "fake company", "is a ghost job"). |

### 3.2 Process model

```text
┌──────────────────────────── Tauri 2 application ─────────────────────────────┐
│  WebView (React/TS UI)  ◄── Tauri commands/events ──►  Rust core            │
│                                                        • WorkerSupervisor    │
│                                                        • IPC bridge+allowlist │
│                                                        • dialogs, app paths   │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │ stdio, NDJSON (one JSON per line, UTF-8)
                                    │ IPC protocol v1  (§15)
┌───────────────────────────────────▼──────────────────────────────────────────┐
│ Python worker (sidecar)                                                      │
│  ipc/ → application/ (use cases) → domain/ ◄── ports ◄── infrastructure/     │
│  plugins/ (connectors, strategies, signals, matchers)                        │
│  scheduler · task queue · rate limiter · SQLite (single writer)              │
│  Playwright browser (child process, only for rendering/autofill)             │
└──────────────────────────────────────────────────────────────────────────────┘
```

Rules:

1. The **worker owns the database**. The Rust layer and frontend never touch SQLite directly.
2. The frontend never orchestrates crawlers; it issues IPC commands and subscribes to events.
3. The worker is supervised: crash → restart with exponential backoff (max 5 restarts / 5 min, then surface a blocking error with "export logs" action). In-flight tasks are marked `interrupted` and may be resumed per task type.
4. Only one worker instance per data directory (lock file).

### 3.3 Packaging and paths

- App data directory (platform-standard, via Tauri `app_data_dir`): `lodestar.sqlite`, `resumes/` (originals, content-addressed), `logs/`, `cache/`, `exports/`, `browser-profile/`.
- The worker receives the data directory path as a CLI argument; it MUST NOT infer or hardcode paths.
- Playwright browsers are installed to `cache/browsers/` on first use of rendered-DOM or autofill features (user-confirmed download, size disclosed).

## 4. Architecture: hexagonal, replaceable, testable

### 4.1 Layers and dependency rule

```text
                 ┌────────────────────────────────────────────┐
                 │  Desktop UI (React)  ──IPC──►  worker/ipc  │   (driving adapters)
                 └────────────────────────┬───────────────────┘
                                          ▼
                 ┌────────────────────────────────────────────┐
                 │ application/  commands · queries ·         │
                 │               orchestration · DTOs         │
                 └────────────────────────┬───────────────────┘
                                          ▼
                 ┌────────────────────────────────────────────┐
                 │ domain/   models · policies · services     │
                 │           ports (Protocols)                │
                 └────────────────────────▲───────────────────┘
                                          │ implements
                 ┌────────────────────────┴───────────────────┐
                 │ infrastructure/ + plugins/  (driven adapters)│
                 │ sqlite · httpx · playwright · pymupdf · onnx │
                 └────────────────────────────────────────────┘
```

**Dependency rule (enforced by tooling):** imports flow only inward.

| Layer | May import | MUST NOT import |
|---|---|---|
| `domain` | stdlib, `domain.*` | `application`, `infrastructure`, `plugins`, `worker`, sqlite3, httpx, playwright, sklearn, fitz, etc. |
| `application` | `domain`, stdlib | `infrastructure`, `plugins` (concrete), `worker` |
| `infrastructure` | `domain`, `application` DTOs where needed, third-party libs | `worker` |
| `plugins` | `domain` (ports/models), shared helpers from `infrastructure` via ports only | other plugins' internals |
| `worker` (composition root + IPC) | everything | — |

Enforce with **import-linter** (contracts in `pyproject.toml`) running in CI and pre-commit. A failing contract fails the build.

> Exception for scoring libraries: numerical helpers (e.g. cosine similarity) used by the domain MUST be implemented with the stdlib or a tiny pure-Python/NumPy-free utility, **or** be accessed through a port (`TextSimilarity`). scikit-learn lives only in `plugins/matching/` and `infrastructure/`.

### 4.2 Required ports

All ports are `typing.Protocol` classes in `app/domain/ports/`. Methods are `async` where I/O is possible. All ports return domain types or `Result` values; they MUST NOT leak third-party types (no `httpx.Response`, no `sqlite3.Row`, no Playwright `Page`).

#### 4.2.1 Shared value types (excerpt)


### 4.4 Composition root and dependency injection

- Exactly one composition root: `app/worker/composition_root.py`.
- It builds an immutable `Container` from typed `AppConfig`, instantiating adapters and injecting them into application services via constructors.
- No service locator, no global singletons, no import-time side effects.
- Tests build alternative containers (`tests/support/containers.py`) with fakes.

```python
def build_container(cfg: AppConfig, *, overrides: Overrides | None = None) -> Container:
    clock = overrides.clock if overrides and overrides.clock else SystemClock()
    http = overrides.http if overrides and overrides.http else PolicyHttpClient(
        inner=HttpxClient(cfg.http), robots=RobotsPolicy(...), limiter=DomainRateLimiter(cfg.crawl), clock=clock)
    uow_factory = overrides.uow_factory if overrides and overrides.uow_factory else SqliteUnitOfWorkFactory(cfg.paths.db)
    registry = PluginRegistry(cfg.plugins)
    register_builtin_plugins(registry)                     # plugins/*/register.py
    ...
    return Container(...)
```

- Feature flags (all in `features`) with defaults:

| Flag | Default | Meaning |

| `features.rendered_dom_extraction` | `true` if browser installed | Allows Playwright-based extraction. |
| `features.local_embeddings` | `false` | Enables ONNX embeddings via `ModelProvider`. |

| `features.external_plugins` | `false` | Reserved; MUST remain unimplemented in MVP. |

### 4.6 Plugin architecture (internal modularity)

A **plugin** is a Python package under `app/plugins/<kind>/<name>/` exposing:

```python
# register.py
PLUGIN = PluginManifest(
    id="ats.greenhouse", kind="connector", version="1.0.0",
    api_version="1",                      # plugin API version this plugin targets
    capabilities={"list_jobs", "fetch_job", "public_api"},
    config_schema=GreenhouseConfig,       # Pydantic model
    network_hosts=("boards-api.greenhouse.io", "boards.greenhouse.io"),   # disclosed in UI
)

def register(registry: PluginRegistry, deps: PluginDeps) -> None:
    registry.add_connector(GreenhouseConnector(deps))
```

Plugin kinds: `discovery`, `connector`, `extraction`, `matching`, `posting_signal`, `risk_model`, `resume_parser`, `keyword`, `browser`, `form_filler`.

**PluginRegistry** responsibilities:

- Registers plugins by `(kind, id)`; rejects duplicate IDs and incompatible `api_version`.
- Resolves ordered lists (e.g. extraction strategies by `default_order` + user override).
- Persists enabled/disabled state and config in `plugin_registry` / `plugin_config`.
- Exposes capabilities (`plugins.get_capabilities` IPC).
- Wraps every plugin call in an **isolation shim**:
  - per-call timeout (default from capability or config);
  - exception capture → `PortError(code="plugin.exception", ...)`;
  - **circuit breaker** per `(plugin_id)`: opens after 5 consecutive failures or ≥50% failures over the last 20 calls; half-open probe after cooldown (default 10 min, exponential up to 6 h); state persisted in `plugin_registry.health_json`;
  - structured log + `crawl_events` row on every failure.
- Adding a plugin MUST require only (a) the new package and (b) one line in the builtin plugin list. No edits to application services, matching, or UI.

### 4.7 Architectural rules (checklist)

1. Every ATS connector implements `JobSourceConnector` and passes the shared connector contract suite.
2. Adding an ATS requires no change to matching, ranking, posting intelligence, or UI.
3. Discovery (finding sources/URLs) and extraction (turning pages into jobs) are independent pipelines joined only by `SourceConfig` and `RawJobRef`.
4. Extraction strategies are independently selectable and ordered (global default + per-source override).
5. Ranking algorithms are replaceable via `ScoringModel` + `MatchingStrategy`.
6. Resume parsers register by MIME type; new formats require only a new `ResumeParser`.
7. Browser automation is abstracted; Playwright is only the first `BrowserProvider`.
8. Persistence is behind repositories.
9. SQLite specifics (rowids, FTS, pragmas, SQL text) MUST NOT appear in `domain/` or `application/`.
10. External HTTP, filesystem, browser, and model access is isolated in infrastructure/plugins.
11. A plugin failure MUST NOT crash unrelated components (isolation shim, §4.6).
12. Configuration is typed; feature flags are explicit.
13. No monolithic classes (soft limit: 400 lines/module, 40 lines/function) and no giant `if/elif` chains over source types — use registries and polymorphism.
14. Every adapter has contract tests.
15. IPC messages, plugin API, DB schema, scoring models, risk models, and taxonomy are versioned.

## 6. Job discovery and extraction

### 6.1 Discovery pipeline

```text
DiscoveryProviders ──► DiscoveredSource ──► SourceRegistry (dedupe, classify ATS)
                                                      │
                                    Scheduler (per-source cadence, budgets)
                                                      ▼
                         CrawlRun ──► Connector.list_jobs ──► RawJobRef stream
```

### 6.2 Discovery providers (initial)

Rules:

- Providers produce `DiscoveredSource` with a `confidence` and `evidence`. Low-confidence sources are held in a "candidate sources" list for user approval; sources the user added explicitly are trusted.
- **Discovery MUST NOT depend on a bundled seed list or on the user adding sources.** At least one enabled provider must enumerate career sites from a live external index on every pass. A seed file may only bootstrap a cold start or seed a test.
- The app MUST NOT assume search engines or web indexes are comprehensive; the UI states coverage is limited to what has been discovered so far.
- **Every registered board is verified by the crawler, not by the provider.** A tenant that no longer exists costs one `crawl.failed` run and is never re-registered (it stays in the source list until the user deletes or disables it).
- Source registration dedupes by canonical URL + connector tenant key.
- "Periodic revisit" uses per-source schedule: default `every 12h` for sources with ≤200 jobs, `every 24h` otherwise, jittered ±10%; user-configurable per source and globally; global caps in §17.

#### 6.2.1 Automatic discovery without seeds

The crux of the product is that **jobs find the user**. Discovery therefore has to keep working on its own: companies appear and disappear, so a fixed list of employers or ATS tenants goes stale by construction.

How one automatic pass works (`discovery.auto_discover`):

1. **Enumerate.** Every enabled provider is asked for candidates. `discovery.web_index` queries a public web URL index for a bounded set of `(ATS host, leading-character bucket)` slices per pass (`discovery.cursor_step`, default 12, walked in parallel — for example "tenants starting with `s` on `boards.greenhouse.io`"). Each query asks for a large block of rows (`discovery.web_index_limit`, default 200, for Common Crawl; `discovery.web_index_cdx_limit`, default 10,000, for CDX) because a small limit samples a fraction of a percent of a bucket: measured, CDX returns 10,001 rows in ~13 s and one such answer reduces to ~100 distinct tenants. The index reflects pages a crawler recently fetched, so it tracks companies that exist rather than a snapshot of a data file. If the primary index (Common Crawl) cannot serve a slice, the Internet Archive CDX API is queried as fallback, with one retry while the pass still has budget; if every index fails for every slice, the slice range is retried next pass.
2. **Rotate.** The pass persists an integer rotation cursor in `app_settings` (`auto_discover_state`) and advances it by `discovery.cursor_step` (default 12). Hosts are walked before buckets, so consecutive passes cover different tenants, and the cursor wraps once the whole space has been visited - a later pass re-checks it with fresher index data.
3. **Register.** Candidates are deduped by canonical URL against existing sources and capped by `discovery.max_new_sources_per_run` (default 200). Each new row gets the default per-source schedule with jitter.
4. **Crawl what is due.** Sources are crawled stalest-attempt-first, bounded by `discovery.max_crawl_sources_per_run` (default 60) and run concurrently up to the global crawl concurrency cap, so a pass stays bounded no matter how many sources exist. A source is "due" when it has never been crawled or when its own interval has elapsed.
5. **Persist.** The completion time and the cursor are written together, so a restarted worker resumes both the daily cadence and the covered ground.
6. **Cold start.** When no run state exists yet (first-ever launch), the worker runs `discovery.warmup_passes` (default 5) passes back-to-back, each still obeying its own budgets and the shared crawl gate, so the bundled seed list is registered in minutes rather than over the first days. The loop stops early once a pass registers nothing new. After that the cadence is the normal daily one.

Additional providers may add candidates (user URLs, company-name resolution, local lists, sitemaps, optional search engines). They all feed the same dedupe, cap and crawl-due machinery, so adding a provider never widens a pass beyond its budget.

Coverage limits that MUST be stated in the UI and docs: the index lags reality (a brand-new company can take weeks to appear), some ATS hosts publish no public boards, and the crawl budget means a large source list is visited over several passes rather than at once.

#### 6.2.2 Hosts whose tenant is a subdomain (Workday, iCIMS) or in the path (UKG Pro)

The M2 connectors read Workday (`{tenant}.wd{N}.myworkdayjobs.com/{locale}/{site}`) and iCIMS (`{tenant}.icims.com`) boards. UKG Pro/UltiPro (`{host}/{tenant}/JobBoard/{boardId}`, §6.4) puts both the employer code and the board id in the path. The variable part of these URLs comes *before* the fixed host or needs two path segments, so a `host/{bucket}` prefix query cannot construct the board URL.

`discovery.domain_index` now covers this space in the live rotation:

1. **Query by domain.** For subdomain ATSs (Workday, iCIMS, BambooHR, Eightfold) it asks the CDX API for `matchType=domain` with `filter=original:^https?://{bucket}`, so a slice is the tenants starting with one letter. UKG Pro (`recruiting.ultipro.com`) and Workable (`apply.workable.com`) use a prefix query instead, because the fixed host is the domain.
2. **Rebuild the board from the full URL.** iCIMS and BambooHR need only the subdomain (board root, or `/careers`). UKG Pro takes `{tenant}/JobBoard/{uuid}`. Workable takes the first path segment. Workday is the hard case: the hostname gives the tenant and `wd{N}` shard, but CxS also needs the `{locale}/{site}` path, so the board URL comes from the indexed path. A bare Workday root answers HTTP 406, which is why hostname-only discovery would not work. Indexed asset and API paths (`/favicon.ico`, `/wday/cxs/...`) are discarded, and `/{site}` plus `/{locale}/{site}` collapse to one board so a tenant is not crawled twice.
3. **Rotate, because domain scans are expensive.** Measured: a Workday domain slice answers in ~42 s, BambooHR in ~50 s, and an iCIMS slice returned a gateway 504 after 60 s. A pass therefore walks three slices, concurrently, with an 85 s per-slice timeout and a single attempt; a failed slice is logged as `discovery.domain_index.cdx_failed` and re-walked when the rotation wraps. The pass cursor still advances, so one throttled ATS does not stall the others. The full sweep is ~156 slices, so this path is slower than the fixed-host rotation by design — but it is seed-free and self-advancing.
4. **Carry the tenant key through discovery.** `DiscoveredSource.tenant_key` → `SourceRegistry.add(tenant_key=…)` → `SourceConfig.ats_tenant_key`, which `ats.workday` already prefers over parsing the URL.

Oracle Recruiting Cloud is enumerated by a separate provider, `discovery.oracle_recruiting`. ORC career sites live on tenant subdomains of an Oracle HCM pod (`{tenant}.fa.{region}.oraclecloud.com/hcmUI/CandidateExperience/{lang}/sites/{site}`). Certificate transparency is useless here because the pods use wildcard certificates, and a whole-`oraclecloud.com` query returns 504. A domain query scoped to one pod, filtered to `/hcmUI/CandidateExperience/`, answers in **17–38 s** and returns full URLs, so the provider rotates a list of HCM pods, two per pass, parses the host and site code, and registers the board. A throttled or retired pod is logged and revisited when the rotation wraps.

`scripts/build_seed.py` still reaches Workday/iCIMS/UKG tenants for the warm start:

1. Query by domain. `matchType=domain` sorts the whole domain; CDX ignores `offset` but supports `showResumeKey=true`, and the resumption key walks the domain in 10,000-row chunks (measured: Workday chunks answer in 30–50 s). A negative `filter=original` drops what would otherwise fill the first chunks: one Workday tenant can own tens of thousands of `/assets/…` URLs, and iCIMS' own `www` marketing site dominates the alphabetical head. Positive `filter=urlkey:…` / `filter=original:^https?://…` narrowing is not used; it returned 503/504 under load.
2. Derive the board URL and tenant key per host. iCIMS: the subdomain is the tenant and the board root is enough. Workday: the subdomain is the tenant, the host carries the `wd{N}` shard, and CxS needs both the tenant and the `{locale}/{site}` path, so the board URL is stored together with its `tenant_key`.
3. Carry the tenant key through discovery. `DiscoveredSource.tenant_key` → `SourceRegistry.add(tenant_key=…)` → `SourceConfig.ats_tenant_key`, which `ats.workday` already prefers over parsing the URL. The seed rows carry `tenant_key` where the URL alone is ambiguous.

Verification is per connector and uses the same public surface the connector crawls: Workday's CxS `POST …/jobs` (its `total`), and iCIMS' `jobs/search?ss=1&in_iframe=1` page, counting posting links and rejecting tenant portals that redirect to `login.icims.com`. UKG Pro boards are harvested with a `matchType=domain` CDX query filtered to `/JobBoard/` paths, then verified with the board's own `POST …/LoadSearchResults` (its `totalCount`); an unknown board id answers 404. A live board with zero postings stays; a tenant whose portal is behind a login does not.

The seed file remains a snapshot — a warm start, not the engine. §6.2's rule that discovery must not depend on it holds: a new Workday, iCIMS, BambooHR, Eightfold, UKG Pro or Workable tenant is picked up by `discovery.domain_index` without regenerating the seed.

### 6.3 Source classification

`SourceClassifier` asks every registered connector `matches(url, sniff)` (URL patterns first, then optional lightweight page sniff) and picks the highest confidence ≥ 0.6; otherwise assigns `connector_id = "generic"` and relies on the universal extraction pipeline (§6.5). Classification result and evidence are stored on the source.

### 6.5 Universal extraction pipeline

Ordered strategies (each independent; each returns `ExtractionResult` or `PortError`):

| Order | Strategy ID | Description |
|---|---|---|
| 10 | `extract.public_api` | Documented public API (via connector). |
| 20 | `extract.public_endpoint` | Publicly accessible structured endpoints discovered on page (e.g. `__NEXT_DATA__`-referenced JSON URLs, `application/json` feeds, sitemap-linked feeds). |
| 30 | `extract.jsonld` | Schema.org `JobPosting` in `<script type="application/ld+json">` (handle `@graph`, arrays, malformed JSON recovery). |
| 40 | `extract.embedded_json` | Hydration state: `__NEXT_DATA__`, `__NUXT__`, `window.__INITIAL_STATE__`, Apollo state, inline JSON blobs matching job-like shape. |
| 50 | `extract.static_html` | CSS/XPath + semantic heuristics (headings like "Responsibilities"/"Qualifications", `<h1>` as title, `itemprop`, microdata, OpenGraph). |
| 60 | `extract.rendered_dom` | Playwright-rendered DOM (only if feature enabled and static strategies yielded insufficient fields), then re-run static/embedded extraction on rendered HTML. Respects robots/ToS and never solves CAPTCHAs. |
| 70 | `extract.generic` | Heuristic text-block scoring (largest coherent content block, title from `<h1>`/`<title>`, location regex, "posted"/"apply by" patterns). |
| 90 | `extract.partial` | Always succeeds: record containing URL, source, any title/employer found, `extraction_status='partial'`, confidence low. |

Pipeline algorithm:

```text
for strategy in ordered(strategies for source):          # per-source override honored
    if not strategy.can_attempt(target): continue
    result = isolated(strategy.extract)                   # timeout, exception capture
    record extraction_results row (status, fields_found, error, duration, bytes)
    merge(result) into accumulator using field-level precedence:
        higher-confidence value wins; ties → earlier strategy wins; never overwrite non-empty with empty
    if accumulator.satisfies(completeness_policy):        # title + description + company + (location or remote flag)
        break
else:
    use partial strategy
extraction_confidence = weighted mean of field_confidence (weights: title .2, description .35, company .1, location .15, posted_at .05, salary .05, apply_url .1)
status = complete if completeness_policy satisfied else partial
```

Preserved on every result: original URL, source ID, employer, available title/description/location/posting date, status, confidence, and per-field provenance (which strategy produced which field).

### 6.6 Responsible crawling

Implemented by a `PolicyHttpClient` decorator wrapping the raw `HttpClient` (so connectors cannot bypass it):

| Policy | Behavior |
|---|---|
| Robots | Fetch/cache `robots.txt` per origin (24 h TTL, refresh on 5xx with bounded retry). Honor `User-Agent` groups, `Disallow`, `Allow`, `Crawl-delay`. Disallowed URL → `PortError(code="robots.disallowed")`, logged in `crawl_events`, **never retried**. If robots.txt is unreachable (5xx/timeouts) treat as "temporarily deny" for that origin with backoff; 404 → allow. |
| User-Agent | Honest and identifiable: `Lodestar/{version} (+local-desktop; contact: configurable)`. No spoofing browsers for HTTP crawling. |
| Rate limits | Per-origin token bucket: default 1 request/second, burst 2, max 2 concurrent per origin; honor `Crawl-delay` if larger. Global concurrency cap (default 8). |
| Retry | Retryable: network errors, 408, 425, 429, 500, 502, 503, 504. Exponential backoff with full jitter: `min(cap, base * 2^n)`; base 2 s, cap 5 min, max 4 attempts per request. `Retry-After` (seconds or HTTP-date) always wins and also pushes the origin's next-allowed time. |
| Auth boundaries | A 401/403, login redirect, or `auth_required` detection stops that URL; mark `EndpointState.auth_required`; never attempt credentials. |
| Anti-bot | Detect common challenge pages (CAPTCHA, "verify you are human", 403 with challenge markers). Record `blocked`; **do not bypass**; back off the origin (e.g. 6 h, doubling to 7 d). |
| Terms | Per-source `terms_notes` field; sources can be marked `crawl_allowed=false` by the user. Built-in connectors use only public endpoints intended for public consumption. |
| Failure handling | A failed crawl never disables a source permanently. Consecutive-failure counter drives backoff of the *schedule* (up to 7 days) and a "needs attention" UI badge; success resets it. |
| Conditional requests | Use `ETag`/`If-None-Match` and `Last-Modified` where available; cache metadata in `source_configs.cache_json`. |
| Caching & dedup | In-flight request coalescing (same URL requested once); response cache keyed by URL+validators. |
| Size/time caps | Per response `max_bytes` (default 5 MB), per request timeout 20 s, per source run caps (requests, duration). |

### 6.7 Crawl orchestration

- `CrawlRun` has statuses from §5.2; each source gets a `crawl_run` row (or a parent run with per-source children for multi-source "run all").
- Steps per source: classify (once) → list refs → diff against known aliases → fetch only new/changed refs → extract → normalize → resolve identity → persist (single UoW per job) → emit observations → mark absent jobs.
- **Not-seen handling:** a known alias absent from a full, successful listing gets a `not_seen` observation. After `N=2` consecutive successful full listings without it (≥ 24 h apart), job `posting_status` → `removed` (history preserved). Partial/failed listings never create `not_seen` observations.
- Progress events: `discovery.progress` (counts: sources total/done, refs discovered, fetched, new, updated, unchanged, failed), `discovery.source_completed`, `discovery.error`.
- Cancellation: cooperative; in-flight HTTP is cancelled; committed jobs remain; run ends `cancelled`.
- After persistence, the orchestrator publishes domain events that trigger (debounced, background priority) keyword extraction, matching for active search profiles, and posting-intelligence evaluation for changed jobs.

### 6.8 Relevance-ranked discovery funnel (Milestone 6)

Board-first discovery (§6.2) answers *"which companies are hiring?"* but not *"which postings matter to this user?"* — the US economy adds on the order of 165k net jobs per month, and crawling every board at full depth does not scale to that. The funnel reallocates the same crawl budget by **relevance**, so that the moment a posting the user could plausibly get appears, it is surfaced without the user searching for it. Four stages:

1. **Board discovery (shipped in M4).** The web-index provider enumerates ATS tenant boards; every discovered company enters the source registry with a default schedule.
2. **Job-URL harvesting.** The *same* index queries that list tenants also list posting URLs (`boards.greenhouse.io/<tenant>/jobs/<id>`). A funnel pass harvests newly indexed posting URLs directly — postings become visible within the index's freshness window (days) **before** their board is ever crawled at full depth, and long-tail companies may never need a full crawl at all.
3. **Relevance tiers.** Sources are ranked against the candidate profile and hard filters from M5/M3 (skills, roles, locations, connector confidence, posting-intelligence signals from M8 as they arrive). The registry assigns each source a tier:
   - **hot** — crawled every pass (the "apply the moment it appears" SLA),
   - **warm** — crawled daily,
   - **cold** — crawled weekly, or index-only (verify individual harvested postings instead of listing the board).
4. **Posting verification.** A harvested posting URL is verified with a single fetch + extraction pass (cheap, one request) and resolved through the M3 identity/fingerprint machinery against the same company's other listings, so harvesting a long-tail company costs one request, not a board crawl. Full listings remain the source of truth for `not_seen`/removal logic; harvested-only postings carry a "via index" provenance until a full listing confirms them.

**Budgets stay the boundary.** The funnel never raises the pass caps: `max_new_sources_per_run`, `max_crawl_sources_per_run`, and the global crawl gate are unchanged; tiering only decides *which* due sources are picked and *how often* each tier is crawled. Index harvests add posting candidates, not crawl load, up to `discovery.funnel_postings_per_pass` verifications per pass.

**Freshness honesty.** A web index reflects what its crawler saw days ago; the hot tier exists because the index alone cannot guarantee "the moment it comes out" for the most relevant boards. The funnel is therefore a coverage amplifier (long-tail companies at near-zero crawl cost), not a replacement for the hot tier's direct polling. This is a deliberate trade-off documented in ADR-0006.

## 7. Normalization, deduplication, and repost detection

### 7.1 Normalization

`JobNormalizer` MUST:

- Strip HTML to text (preserving list/heading structure as lightweight markers), normalize whitespace and Unicode (NFKC), remove tracking params from URLs.
- `normalized_title`: lowercase, remove bracketed noise (`(Remote)`, `- US`, req IDs), expand abbreviations (`Sr.`→`senior`, `SWE`→`software engineer`, `Eng`→`engineer`), collapse roman/numeric levels (`Engineer II` → level 2 kept as attribute), map to `title_family` via taxonomy.
- Parse location into structured parts; detect remote/hybrid from text and structured fields; keep raw text.
- Parse salary text/ranges and periods (`hour`, `year`, `month`), annualize using documented factors (2080 h/yr, 12 mo), keep raw text, currency detection by symbol/code.
- Infer `Seniority` from title and, with lower confidence, from years-of-experience requirements.
- Split description into sections (responsibilities, qualifications/requirements, preferred/nice-to-have, benefits, about) with a rule-based sectioner; `required_skills`/`preferred_skills` come from section-aware keyword extraction (§12).
- Compute fingerprints (§7.2).

### 7.2 Fingerprints

| Fingerprint | Computation | Use |
|---|---|---|
| `url_key` | canonical URL: lowercase host, strip fragments/tracking params/trailing slash, collapse ATS URL variants to `(ats, tenant, posting_id)` where known | exact alias match |
| `ats_key` | `(ats_id, tenant_key, source_posting_id)` | exact alias match |
| `company_key` | resolved `company_id` | scope |
| `title_key` | `normalized_title` + level attribute | blocking and scoring |
| `location_key` | sorted normalized (city, region, country) set + workplace type | scoring |
| `desc_exact_hash` | SHA-256 of normalized description text (lowercase, whitespace-collapsed, boilerplate removed) | identical content |
| `desc_simhash64` | 64-bit simhash over word 3-shingles | near-duplicate (Hamming ≤ 6 = near-identical) |
| `desc_minhash` | 64 permutations over 5-shingles (Jaccard estimate) | similarity scoring |
| `embedding` (optional) | `ModelProvider.embed` on title + first 1,500 chars | semantic similarity (feature-flagged) |

**Boilerplate removal:** strip company-wide "About us", EEO statements, and benefits blocks by learning per-company repeated paragraphs (paragraphs appearing in ≥ 60% of ≥ 5 jobs of the same company) so that fingerprints focus on job-specific content.

### 7.3 Job identity resolution

`JobIdentityResolver.resolve(incoming)` returns an `IdentityDecision`:

```python
@dataclass(frozen=True, slots=True)
class IdentityDecision:
    action: Literal["attach_alias", "new_snapshot", "new_job", "link_related"]
    job_id: str | None
    repost_class: RepostClass
    confidence: float
    evidence: Sequence[Evidence]
    related_job_ids: Sequence[str] = ()
```

Algorithm (ordered; first decisive rule wins, scoring otherwise):

1. **Exact alias hit:** `(source_id, source_posting_id)` or `url_key` matches an existing alias → same job.
   - `desc_exact_hash` equal → `exact_duplicate`, append `seen` observation, update `last_seen_at`.
   - Differs → `materially_updated` if change magnitude ≥ threshold (below), else treat as minor edit; create new snapshot either way, update `last_meaningful_change_at` only if material.
2. **Candidate retrieval (blocking):** same `company_id`, and (`title_key` equal, or `title_family` equal, or FTS title similarity above floor) within lookback `repost_lookback_days` (default 365, includes removed jobs).
3. **Pairwise similarity** via `DeduplicationStrategy` implementations producing evidence; combined score:

```text
sim = 0.30*title_sim + 0.15*location_sim + 0.40*desc_sim + 0.10*dept_sim + 0.05*salary_sim
desc_sim = max(jaccard_est(minhash), 1 - hamming(simhash)/64 adjusted, cosine(embedding) if enabled)
```

4. **Decision table** (all thresholds configurable under `dedup.*`; defaults shown):

| Condition | Class / action |
|---|---|
| `desc_exact_hash` equal AND title_sim ≥ 0.95 AND location_sim ≥ 0.8, new alias/URL/ID | `reposted_identical` → attach alias to existing job; create `repost_events` row |
| `sim ≥ 0.90` AND title_sim ≥ 0.9 AND location_sim ≥ 0.8 AND desc_sim ≥ 0.90 | `reposted_identical` (high-confidence near-identical text) |
| `0.75 ≤ sim < 0.90` AND title_sim ≥ 0.9 AND location_sim ≥ 0.8 | `materially_updated` repost: attach alias, new snapshot, `repost_events` with `material=true` |
| `0.60 ≤ sim < 0.75`, or title_family equal but different level/team/location | `similar_distinct`: create new job, add `job_relations(relation='similar')` |
| otherwise | `new_position` |

5. **Guards against over-merging:**
   - Different `location_key` (non-remote) or different team/department markers (`department` mismatch) caps class at `similar_distinct`.
   - Different explicit requisition IDs found in text → never merge unless one is absent.
   - Multiple candidates tie → choose highest `sim`; if the top two are within 0.03, prefer `similar_distinct` and flag `ambiguous=true` for UI review.
   - Companies often post N openings of the same role (different locations/reqs): never collapse jobs that are simultaneously active with different ATS IDs **and** different locations/req IDs.
6. All decisions persist evidence (`repost_events.evidence_json`, `job_relations.evidence_json`) and confidence. Users may **manually merge/unmerge** jobs; manual decisions override automation and are never reversed by it.

**Material change threshold:** a change is *material* if `1 - jaccard(shingle5) ≥ 0.10` on job-specific text, or title/location/salary/seniority changed, or requirement sections changed (≥ 1 skill added/removed).

### 7.4 Repost events

`repost_events` rows: `job_id`, `previous_alias_id`, `new_alias_id`, `detected_at`, `class`, `confidence`, `url_changed`, `ats_id_changed`, `posted_date_reset` (new `posted_at` later than prior while content identical), `material`, `evidence_json`. These feed posting intelligence (§9) and suppression (§8).

## 8. Application history and company-aware suppression

### 8.1 Application tracking

An `Application` records: company, job, **job title snapshot**, **job snapshot at application time** (`job_snapshot_id`), application date, status, resume version, notes, related reposts (via job aliases/relations), and an append-only event log.

Statuses (from §5.2): `interested`, `saved`, `applied`, `acknowledged`, `recruiter_contacted`, `interviewing`, `rejected`, `withdrawn`, `offered`, `accepted`.

- `interested` and `saved` are *pre-application* states; they **never** set `applied_at` and **never** start a cooldown.
- Entering `applied` (manual user action, or user confirmation after autofill) sets `applied_at` (user-editable date) and creates an `application_events` row.
- Status updates are manual; transitions are free-form (users can correct mistakes) but every change is an event (`status_changed`, from, to, at, note).
- Outcomes (`application_outcomes`) are separate records capturing `OutcomeKind`, date, and optional notes, used by analytics (§9.9). `no_response` can be recorded by the user or *proposed* by the app after a configurable period (default 30 days since `applied`) — proposals require user confirmation.
- Dismissed/hidden jobs live in `job_user_state`, not in `applications`.

### 8.2 Suppression policy

Policy fields (stored in `suppression_policies`, one active default plus optional per-search-profile overrides):

| Field | Default |
|---|---|
| `exact_repost_suppress` | `true` (indefinite while the applied job's repost chain exists) |
| `similar_role_cooldown_days` | `180` |
| `similar_role_threshold` | `0.75` (uses §7.3 `sim` + title-family equality) |
| `company_wide_cooldown_enabled` | `false` |
| `company_wide_cooldown_days` | `90` (used only if enabled) |
| `different_role_same_company` | `allow` |
| `re_evaluate_on_expiry` | `true` |

Rules (evaluated only against applications whose `applied_at` is not null; see rule 7 for how later statuses such as `withdrawn` or `rejected` affect cooldowns):

1. **Trigger:** only an application that reached `applied` (has `applied_at`). Saving, dismissing, or marking interested MUST NOT create a cooldown. Test-enforced.
2. **Exact repost** of an applied job (same job via alias chain or `reposted_identical` classification) → suppress, reason `exact_repost_of_applied`.
3. **Similar role** at the same company: for incoming/existing job J and application A with `applied_at + 180d > now`: if `title_family(J) == title_family(A.job)` and `sim(J, A.job_snapshot) ≥ threshold` → suppress, reason `similar_role_cooldown`, `expires_at = applied_at + cooldown`.
4. **Different role** at same company → not suppressed (default).
5. **Company-wide** (if enabled) → all jobs at company suppressed until `applied_at + company_wide_cooldown_days`, reason `company_wide_cooldown`.
6. **Expiry:** at `expires_at`, suppression state becomes `expired` and the job is re-evaluated (matching and posting intelligence rerun; job reappears in normal views, tagged "previously applied to similar role").
7. **Withdrawn / rejected / offered / accepted:** the cooldown still counts from `applied_at` (default). A policy toggle `rejected_shortens_cooldown_days` MAY be added later; not in MVP.
8. **Manual restore:** user can restore any suppressed job at any time → `state='restored'`; the automation never re-suppresses that job/policy pair unless the user clears the restore.
9. Suppression NEVER deletes data. Suppressed jobs are hidden from default result lists but searchable in the dedicated view.
10. Each suppression stores a `suppression_evidence` set: the triggering application, the similarity breakdown, the policy snapshot (values), and human-readable explanation text.

Evaluation timing: at ingestion of new jobs/aliases, on policy change, on application create/status change (applied), and daily for expiries.

### 8.3 Suppressed/Seen jobs view requirements

A dedicated view lists, with filters and explanation per row: previously seen jobs, duplicates, reposts, recently applied-to roles, suppressed jobs (with expiry date), expired suppressions, and restored jobs. Each row shows *why* (reason code + sentence), the linked application, and a "Restore" action.

## 9. Posting Quality & Hiring Activity Intelligence

**Purpose:** reduce wasted application effort by identifying postings that are potentially stale, inactive, recycled, or misleading — **without claiming certainty**. This subsystem is independent of discovery, matching, and application tracking: it reads history through `ObservationRepository`/`JobRepository` ports and writes only observations, signals, assessments, and company summaries.

### 9.1 Principles

1. An old posting alone is not a ghost job.
2. Missing data is *missing*, not negative.
3. **Risk and confidence are separate outputs.**
4. Every output carries evidence and the model identity/version.
5. Weights and thresholds are configurable and documented.
6. Company-level conclusions require adequate samples.
7. Language is cautious; no accusations.
8. History is append-only; assessments are reproducible from stored signals + model version + config hash.

### 9.2 Signal provider contract

```python
@dataclass(frozen=True, slots=True)
class SignalResult:
    signal_id: str                 # stable ID, e.g. "signal.repost_frequency"
    provider_version: str
    description: str
    status: SignalStatus           # available | missing | error
    risk_contribution: float | None        # 0..1; None iff status != available
    confidence: float                       # 0..1 (0 when missing)
    strong: bool                            # true only for explicit, high-reliability evidence
    evidence: Sequence[Evidence]
    evidence_source: str                    # e.g. "observations.endpoint_checks"
    observed_at: datetime                   # time of the most recent underlying observation
    evaluated_at: datetime
    missing_reason: str | None
    explanation: str                        # one sentence, cautious language
```

Rules for every provider: pure function of `JobHistory` + `SignalContext` (clock, config, cohort stats); deterministic; never raises for absent data (returns `missing`); never mutates state; unit-tested with golden fixtures.

`JobHistory` includes: job, aliases, snapshots (ordered), observations, repost events, endpoint observations, related jobs, company summary (if sufficiently sampled), cohort stats provider.

### 9.3 Initial signal providers

Default weights `w`, availability rules, and contribution mappings below are **initial heuristics** (model `risk.heuristic_v1`), documented for transparency and tunable.

| ID | w | What it measures | Available when | Risk contribution `r` | Confidence `c` |
|---|---:|---|---|---|---|
| `signal.posting_age` | 0.10 | Time since first observed (and source posting date if trustworthy), relative to comparable roles and the employer's history | job has `first_seen_at` | `ratio = age_days / cohort_median_days`. With cohort (≥15 closed comparable postings, else company median with ≥8, else absolute fallback): `r = clamp((ratio − 1.5)/4.5, 0, 1)`. Absolute fallback: `age<30d→0`; `30–90d` linear to `0.3`; `>90d` linear to `0.5` at 180d. **`r` capped at 0.5** for this signal (age alone never implies high risk). | cohort 0.70; company 0.55; fallback 0.35; multiplied by `min(1, observed_window_days/14)` |
| `signal.last_meaningful_change` | (part of content_staleness) | Time since last material snapshot change | ≥2 snapshots or observed ≥14 d | see content staleness | |
| `signal.repost_frequency` | 0.20 | Reposts, intervals, date resets, ID/URL changes, identical descriptions | observed ≥1 full crawl cycle | `n_ident` = reposts in last 365 d with `reposted_identical`; `n_reset` = posted-date resets; `r = min(1, 0.20*n_ident + 0.10*n_reset + 0.10*n_idchange_only)`; if median interval between reposts < 45 d and `n_ident ≥ 2`, add `0.15` (cap 1) | `min(1, observed_days/90) * 0.8` (min 0.15 when available) |
| `signal.endpoint_availability` | 0.25 | Page reachability, application form availability, closed messaging, contradictions with the employer's own site | ≥1 endpoint observation in last `endpoint_obs_max_age_days` (default 14) | `ok→0.0`; `form_unavailable→0.70`; `generic_redirect→0.60`; `closed_message→0.95`; `gone_404_410→0.90`; transient (`timeout`,`error`) require ≥2 consecutive failures → `0.40`, else *missing*; `blocked`/`auth_required` → *missing* (never negative evidence) | `ok 0.60`; `closed_message 0.90`; `gone 0.85`; `form_unavailable 0.60`; `generic_redirect 0.50`; decays linearly to 50% of value over the max age window; `strong=true` for `closed_message` and `gone_404_410` |
| `signal.content_staleness` | 0.10 | Unchanged description over time; copy across positions; genericness; missing job-specific info | ≥14 d observed OR single-snapshot content analysis possible | `r = 0.35*unchanged_factor + 0.25*copy_factor + 0.25*generic_factor + 0.15*missing_specifics_factor` where `unchanged_factor = clamp((days_unchanged − 60)/180,0,1)` (only if ≥3 crawls), `copy_factor` = share of other same-company jobs with desc similarity ≥ 0.9 (needs ≥5 company jobs), `generic_factor` from boilerplate ratio and absence of concrete tools/responsibilities, `missing_specifics_factor` = no requirements/responsibilities sections | 0.45 typical; 0.30 if only single-snapshot analysis |
| `signal.duplicate_consistency` | 0.10 | Cross-source agreement: contradictory titles/locations/compensation; different statuses | ≥2 aliases from distinct sources | `r = 0.8` if any source shows closed while another active; else `min(0.6, 0.15*n_conflicts)`; `0` if consistent | 0.5; 0.8 when closed-vs-active conflict |
| `signal.company_hiring_activity` | 0.15 | Employer-level patterns (§9.7) | company summary meets sample thresholds | map company `repost_ratio`, `inactive_ratio`, `median_duration` vs. global priors to `r ∈ [0,0.7]` (company never contributes > 0.7) | `min(0.6, 0.15 + n_unique/60)` |
| `signal.explicit_closure_language` | 0.30 | Text such as "no longer accepting applications", "position has been filled", "this job has expired" (configurable multi-language pattern list with negation handling) | any snapshot text/page available | `0.95` when match; `0` if page text fully inspected and no match (confidence low) | match 0.90; no-match 0.25; `strong=true` on match |
| `signal.implausible_requirements` | 0.05 | Contradictory/unrealistic requirements (e.g. years of experience exceeding technology age per a bundled table; entry level with ≥8 years) | requirement text parsed | `0.6` per distinct contradiction (cap 0.8) | 0.35 |

Notes:
- "Repeated advertisements for identical positions" is captured by `signal.repost_frequency`; "contradictory hiring information" by `signal.duplicate_consistency` and `signal.endpoint_availability`.
- Endpoint checks are performed by a **polite verifier** in the orchestration layer (HEAD/GET of job page and detection of application availability, never submitting anything), scheduled with a budget (default: check each *active, in-profile* job at most every 7 days, plus on demand "Verify now").

### 9.4 Risk aggregation (`risk.heuristic_v1`)

Inputs: `SignalResult[]` (all registered providers), `RiskModelConfig`.

```text
available = [s for s in signals if s.status == available]
W_all   = Σ_i w_i                      # over all registered, enabled providers
W_avail = Σ_i w_i  (available)
weighted evidence mass M = Σ_i w_i * c_i                (available)

# 1) Evidence-weighted risk with a weak prior (shrinks low-evidence cases toward prior)
risk_agg = (w0 * r0 + Σ_i w_i * c_i * r_i) / (w0 + M)       defaults: w0 = 0.15, r0 = 0.20

# 2) Strong-evidence floor (explicit closure / gone page)
if any(s.strong for s in available):
    risk = max(risk_agg, max(r_i for strong s) * 0.95)
else:
    risk = risk_agg

# 3) Confidence (separate): coverage and quality
coverage = W_avail / W_all
quality  = (Σ_i w_i * c_i) / W_avail            (0 if W_avail == 0)
confidence = clamp(0.5*coverage + 0.5*quality, 0, 1)
if any strong signal: confidence = max(confidence, 0.70)
if W_avail == 0: confidence = 0

# 4) Conflict penalty on confidence
if signals disagree strongly (max r_i − min r_i ≥ 0.7 among signals with c ≥ 0.5): confidence *= 0.85
```

Worked examples (must exist as unit tests):

1. Only `posting_age` available (`r=0.5, c=0.40, w=0.10`): `risk_agg = (0.15*0.2 + 0.10*0.40*0.5)/(0.15+0.04) ≈ 0.26`, confidence ≈ `0.5*(0.10/1.25)+0.5*0.40 = 0.24` → *Needs verification*, **not** high risk.
2. Only `explicit_closure_language` match (`r=0.95,c=0.90,w=0.30`, strong): `risk = max(≈0.68, 0.90) = 0.90`, confidence ≥ 0.70 → *Likely inactive / potential ghost job*.
3. No signals available → `risk = 0.20` (prior), confidence 0 → *Needs verification* with "insufficient evidence" label.

### 9.5 Classification (documented thresholds)

Evaluated in order; all thresholds configurable (`posting_intelligence.thresholds`):

| Class | Rule |
|---|---|
| `likely_inactive` ("Likely inactive / potential ghost job") | `risk ≥ 0.75` AND `confidence ≥ 0.50` |
| `likely_stale` | `0.50 ≤ risk < 0.75` AND `confidence ≥ 0.40`; OR `risk ≥ 0.75` AND `0.30 ≤ confidence < 0.50` |
| `likely_active` | `risk < 0.30` AND `confidence ≥ 0.35` |
| `needs_verification` | everything else (including all low-confidence cases) |

Rationale (shown in docs/UI "How this works"): *the thresholds are initial, uncalibrated heuristics chosen so that (a) one weak signal can never push a posting above "needs verification", (b) high-risk classes require corroborating or strong evidence, and (c) "likely active" requires enough evidence of activity, not merely absence of red flags.* The app MUST NOT auto-modify thresholds. After ≥ 30 recorded outcomes the calibration view (§9.9) may *suggest* changes the user can accept.

`RiskAssessment` persisted fields: `risk`, `confidence`, `class`, `evidence_sufficiency` (`sufficient` / `limited` / `insufficient`: from coverage), `model_id`, `model_version`, `config_hash`, `evaluated_at`, full signal list (references to `signal_observations`), top contributing signals ordered by `w*c*|r−r0|`.

### 9.6 Reproducibility and history

- Signals are stored in `signal_observations` (immutable).
- `risk_assessments` references the exact `signal_observation` set, `risk_model_versions.id`, and `config_hash`. Re-running the pure `assess()` on stored signals with the same model/config MUST reproduce `risk`, `confidence`, and `class` exactly (golden test).
- `classification_changes` rows are written when the class changes between consecutive assessments (from, to, at, triggering signals).
- Re-evaluation triggers: new snapshot, repost event, endpoint observation, scheduled daily pass for active jobs, config/model change (new assessment, old kept).

### 9.7 Company-level hiring intelligence

For each company maintain `company_hiring_summaries` (periodic immutable snapshots, one per evaluation day at most):

Metrics:

- `n_unique_postings` (distinct canonical jobs observed), `observation_window_days`.
- `n_reposted_positions`, `repost_ratio = reposted / unique`.
- `median_posting_duration_days` (for jobs with observed end: removed/closed; right-censored active jobs reported separately via Kaplan–Meier-style median when `n ≥ 15`, else omitted).
- `n_removed`, `removal_rate`.
- `n_inaccessible_endpoints`, `n_no_change_roles` (no material change > 90 d).
- `n_inactive_assessed` (class `likely_inactive` or `likely_stale` with confidence ≥ 0.5).
- From applications (user's own): `n_applications`, `response_rate`, `interview_rate`, `no_response_rate` with **95% Wilson intervals**.

Sample-size gates (configurable):

| Tier | Condition | Output |
|---|---|---|
| Insufficient | `n_unique < 3` or window `< 21 d` | "Insufficient evidence" — no label, only raw counts |
| Limited | `3 ≤ n_unique < 8` or window `< 60 d` | descriptive counts; label limited to "Limited evidence of active hiring" / "Application activity inconclusive" |
| Adequate | `n_unique ≥ 8` AND window `≥ 60 d` | labels permitted (below) |
| Application stats | shown only if `n_applications ≥ 5`; otherwise "not enough applications to compare" | |

Allowed cautious labels (only at *Adequate*, each with its evidence list):

- "Repeated reposting observed" — `repost_ratio ≥ 0.30` and `n_reposted ≥ 3`.
- "Elevated posting risk" — share of active jobs with class ∈ {`likely_stale`,`likely_inactive`} ≥ 0.40 (confidence-weighted).
- "Limited evidence of active hiring" — median duration ≥ 2× global median **and** ≥ 3 inaccessible/no-change roles.
- "Application activity inconclusive" — applications < 5, or CI width > 0.4.

Never use words implying intent ("scam", "fake", "deceptive"). Each label links to the underlying postings.

### 9.8 Ranking integration (credibility is separate from fit)

Dimensions exposed per job: **Candidate fit**, **Experience alignment**, **Seniority alignment**, **Compensation alignment**, **Location alignment**, **Freshness**, **Hiring activity**, **Posting credibility** (`credibility = 1 − risk`, displayed with confidence).

User-selectable **Credibility policy** (`ranking_policy`, per search profile):

| Mode | Behavior |
|---|---|
| `show_all` | No effect on ordering or visibility; badges only. |
| `deprioritize` (default) | `rank_score = fit × (1 − 0.5 × risk × min(1, confidence/0.5))`. Low-confidence risk has proportionally less effect. |
| `hide_high_risk` | Hide jobs classified `likely_inactive` with confidence ≥ 0.5 (still reachable via "Show hidden") and apply `deprioritize` to `likely_stale`. |
| `require_evidence` | Show only `likely_active`; others reachable via a toggle. |

Rules: weak evidence never discards a posting; every hide/deprioritization has a visible explanation ("Moved down because: …"); users can override per job ("Treat as active"), which records a `user_action` observation kept in history. A user override affects only how that job is *displayed and ranked for that user*; it never alters stored signals, risk, or confidence values.

### 9.9 Outcome feedback and calibration (local, optional)

Data: `application_outcomes` + application snapshots joined to the assessment *as of application date* (`risk_assessments` latest ≤ `applied_at`).

Analyses (feature `outcome_analytics`):

- Response, interview, rejection, no-response rates, and time-to-first-response (median, IQR), each with Wilson intervals, grouped by: posting age bucket, repost count bucket, endpoint state, risk class, company activity tier, fit score decile.
- Display `n` for each bucket; hide buckets with `n < 5`.
- Calibration table: for each risk class, observed response rate vs. overall. Presented as **associations**.
- Copy rules (enforced by a UI string test): "associated with", "observed", never "proves" or "caused". Explicit disclaimer: *no response may reflect many causes, including hiring delays, and does not establish that a posting was a ghost job.*
- `no_response` is never converted into a risk signal automatically. Optionally (after ≥ 30 outcomes) the app can *propose* a modified weight set (`risk.heuristic_v1+local`) for the user to accept; acceptance creates a new `risk_model_versions` row; previous assessments remain.

## 10. Resume parsing and candidate profiles

### 10.1 Import

- Formats: PDF (PyMuPDF), DOCX (python-docx), TXT. Selected by MIME/extension through `ResumeParser` registry.
- Originals are copied into `resumes/` content-addressed by SHA-256 and never modified. File size cap 10 MB; page cap 20 (configurable).
- Multiple **resume versions**: each import creates `resume_files` + `resume_versions` (label, imported_at, parent_version_id, parser id/version, text hash, `is_active`).
- Scanned/image-only PDFs: detect low text yield; show "no extractable text" with guidance (OCR is out of scope for MVP; `ResumeParser` interface permits an OCR plugin later).

### 10.2 Parsing pipeline

```text
bytes → text extraction (layout-aware, column handling, header/footer removal)
      → sectioner (Experience, Education, Skills, Projects, Certifications, Summary)
      → entity extraction (employers, titles, dates, bullets, institutions, degrees)
      → skill extraction (KeywordExtractor + KeywordNormalizer)
      → evidence linking → ParsedResume (with per-field confidence)
```

Extracted: work experience (employer, title, start/end, bullets), job titles, skills, technologies, education, certifications, projects, summary, contact details (stored but never used in matching), `years_experience_total` (computed from merged non-overlapping date ranges; marked `inferred` with confidence).

### 10.3 Skill evidence model

Each profile skill carries:

| Field | Meaning |
|---|---|
| `canonical_skill_id` | taxonomy ID (§12.2) |
| `evidence` | `explicit_with_experience` (listed in Skills AND appears in ≥1 experience/project bullet), `explicit` (listed only), `inferred` (implied: e.g. "Django" ⇒ Python at lower confidence; or only mentioned in a summary), `limited` (single weak mention) |
| `evidence_refs` | spans (section, bullet index, character offsets) |
| `recency_years` / `duration_years` | from linked experience |
| `confidence` | 0..1 |
| `user_status` | `UserSkillStatus` override if set |

Skills are **not** equally important: matching weights use `evidence` strength (§11.3). Inference rules are a versioned data table (`skill_implications`) and are visible/removable by the user.

### 10.4 Manual correction

The Resume Manager UI allows editing: contact info, experience entries, dates, titles, skills (add/remove/merge), evidence levels, and per-skill `UserSkillStatus`. Edits are stored as **overrides** on top of parser output (`profile_overrides`), keep parser output immutable, and are reapplied when a resume version is re-parsed. The app never edits the original resume file and never generates claims the user hasn't entered.

### 10.5 Autofill answer book

A separate `AnswerBook` in the profile holds user-entered answers for common form fields (name, email, phone, address, links, current company/title, education, work authorization/sponsorship if the user chooses to provide them, notice period, desired start date). Demographic/EEO answers are **not stored by default**; there is no feature to auto-answer them (§13).

## 11. Candidate–job matching and ranking

### 11.1 Pipeline

```text
Jobs ──► Hard filters (policy) ──► pass? ──► MatchingStrategies (per dimension) ──► ScoringModel
                │ fail                                                         │
                ▼                                                              ▼
       FilterOutcome (kept, reason)                              MatchResult + explanations
                                                                              ▼
                                                  Ranking policy (credibility, suppression) ──► ordered list
```

Hard filters are **separate** from ranking. Jobs failing hard filters are excluded from ranked lists *according to user settings* (`exclude` or `show_in_filtered_tab`), with the failing rule recorded.

### 11.2 Hard filters (all optional, user-configured per search profile)

Title include/exclude (keywords, regex-safe), seniority set, employment type set, workplace type set, locations/radius/countries, remote-eligible countries, minimum salary (applied only when salary present; `treat_missing_salary_as: pass|fail` default `pass`), excluded companies, required keywords, excluded keywords, posting age max, work-authorization constraints (e.g. "no sponsorship offered"; only if user supplies), industries.

Each filter returns `FilterVerdict(pass|fail|unknown, reason)`; `unknown` follows a per-filter policy (default `pass` for missing data → consistent with "missing ≠ negative").

### 11.3 Scoring dimensions (default model `fit.weighted_v1`)

| Dimension | Strategy ID | Default weight |
|---|---|---:|
| Skills & resume alignment | `match.skills_resume` | 0.35 |
| Experience & seniority | `match.experience_seniority` | 0.20 |
| Responsibilities alignment | `match.responsibilities` | 0.20 |
| Location & workplace | `match.location_workplace` | 0.10 |
| Compensation | `match.compensation` | 0.10 |
| Freshness | `match.freshness` | 0.05 |

Weights are user-editable (`matching.update_weights`), must sum to 1 after normalization, and are stored with every result.

**Dimension definitions** (initial; each returns `score ∈ [0,1]`, `available: bool`, `reasons[]`):

1. **Skills & resume alignment**
   - For each job skill `s` with level `required` (weight 1.0) / `preferred` (0.4) / `mentioned` (0.15), and `idf_weight(s)` (rarer skills count more; bounded 0.5–1.5):
     `evidence_strength(s)`: `explicit_with_experience=1.0`, `explicit=0.8`, `inferred=0.5`, `limited=0.3`; user status override: `have_experience → 1.0`, `learning → 0.4`, `no_experience → 0`, `not_relevant → skill excluded from both numerator and denominator`.
   - `coverage_req = Σ w_s·idf_s·strength_s / Σ w_s·idf_s` over required; same for preferred.
   - `lexical = cosine(tfidf(resume_text_weighted), tfidf(job_text))`, calibrated by percentile against the user's recent job pool.
   - `score = 0.70·(0.80·coverage_req + 0.20·coverage_pref) + 0.30·lexical` (if no preferred skills: `0.70·coverage_req + 0.30·lexical`). Missing-skill list returned in reasons.
2. **Experience & seniority:** `0.5·seniority_fit + 0.3·years_fit + 0.2·title_fit`.
   - `seniority_fit`: ordered ladder distance `d`; `d=0→1.0`, `1→0.7` (slightly higher if job is *more junior* than candidate than more senior? configurable asymmetry: over-qualified `0.7`, under-qualified `0.55`), `2→0.3`, `≥3→0.1`.
   - `years_fit`: if job states min years `m` and candidate `y`: `1.0` if `y ≥ m`; else `max(0, y/m)^1.5`; unavailable if no stated requirement.
   - `title_fit`: similarity between job `title_family`/title and candidate's past/target titles.
3. **Responsibilities alignment:** split job responsibilities into sentences; for each, max cosine similarity to candidate bullets (TF-IDF baseline; embeddings if enabled); `score` = mean of the top-`k` (k=8) per-sentence maxima, calibrated by percentile; reasons cite best-matching bullet pairs.
4. **Location & workplace:** compare candidate preferences (acceptable workplace types, locations, radius, relocation willingness) with job; remote-eligibility respected; `unknown` job location → unavailable.
5. **Compensation:** if job salary available: ratio vs. user's desired minimum/target: `≥ target → 1.0`; between min and target linear 0.6→1.0; `< min → max(0, 0.6·(job_max/min))`; unavailable if no salary.
6. **Freshness:** `exp(−ln2 · age_days/half_life)` with `half_life = 14` d, using `max(first_seen, posted_at if plausible)`; unavailable if unknown.

**Aggregation:** `fit = Σ w_d·s_d / Σ w_d` over **available** dimensions; report `dimension_coverage = Σ w_d(available)`; if coverage < 0.6, show a "limited data" badge. Missing dimensions never score zero.

### 11.4 Persistence and explanation

Each `matching_results` row stores: `model_id`, `model_version`, weights JSON, `fit_score`, per-dimension rows (`matching_dimension_scores`: score, available, weight, details JSON) and `matching_explanations` (reason code, message, evidence refs). The UI explains: strengths, gaps (missing required skills), unavailable dimensions, and how filters/credibility/suppression affected visibility.

Re-evaluation triggers: new/changed job, resume version change, profile edits, weight changes, user skill status change. Results are invalidated by `(model_version, weights_hash, profile_hash, job_snapshot_id)`; stale results are recomputed lazily in the background.

Do not describe fit as the probability of an interview. UI label: "Fit score (heuristic)" with a "How is this calculated?" panel.

### 11.5 Swappable matching strategies

`MatchingStrategy` (per dimension) and `ScoringModel` (aggregation) are separate ports. The optional `match.embedding_similarity` strategy can augment responsibilities/skills when `ModelProvider` is enabled. A user can select the active `ScoringModel` per search profile.

## 12. Keyword intelligence

### 12.1 Extraction

- `KeywordExtractor` combines: (a) dictionary/phrase matching against the taxonomy (with aliases and case/punctuation variants, e.g. `C++`, `C#`, `.NET`, `Node.js`), (b) section-aware context (requirements vs. preferred), (c) light noun-phrase heuristics for unknown candidates (queued in an "unrecognized terms" list; never auto-added to taxonomy).
- `KeywordNormalizer` maps mentions to canonical taxonomy IDs and rejects ambiguous matches by context (e.g. "Go" the language vs. verb; "R"; "Spark" etc. require context cues or adjacent tech terms).

### 12.2 Taxonomy

Versioned data file (`keyword_taxonomy` table seeded from `data/taxonomy/vN.json`): `id`, `canonical`, `category` (language, framework, cloud, database, tool, practice, soft_skill, domain, certification), `aliases[]`, `implies[]` (with strength), `disambiguation` rules, `deprecated_by`. Users can add custom keywords/aliases (stored separately; never altering shipped versions).

### 12.3 Prevalence computation (counts distinct jobs, not observations)

- Unit of counting is a **canonical job** (after dedup/alias merging). Repeated crawl observations and reposts of the same job count once; `reposted_identical` aliases collapse; `similar_distinct` jobs count separately.
- Cohort definition: filters on title family/text, seniority, industry, company, date range (by `first_seen_at` or `last_seen_at` window), and job state (default: not `removed` older than window; suppressed jobs included, since demand analysis isn't about visibility).
- Output per keyword: `n_jobs_with_keyword`, `n_jobs_in_cohort`, `prevalence = n_with / n_cohort`, `required_prevalence` (as required), `preferred_prevalence`, `Wilson CI`, and example jobs. UI text: "TypeScript appears in 68% of the 120 senior frontend engineering postings collected."
- Trend: weekly/monthly series computed over cohorts by `first_seen` bucket with `n` shown; hide points with `n < 10`.
- Stored in `keyword_prevalence_observations` (immutable computed snapshots, keyed by cohort hash + computed_at) for historical comparison; recomputed incrementally.

### 12.4 Resume coverage

For each keyword in the cohort, classify: **covered** (`explicit_with_experience`/`explicit`), **weak evidence** (`inferred`/`limited`), **not mentioned in resume** (absence of mention ≠ absence of ability), **user-declared** status (`have_experience`, `learning`, `no_experience`, `not_relevant`). Missing-skill ranking: `gap_score = prevalence × (required_share + 0.4×preferred_share) × (1 − strength)`, excluding `not_relevant`.

Constraints: the app MUST NOT fabricate experience or modify resumes automatically. Suggestions are phrased as "Often requested; not found in your resume — add it only if it reflects real experience." Users may mark each skill's status; these statuses feed matching (§11.3).

## 13. Browser automation and safe autofill

### 13.1 Abstractions

- `BrowserProvider` (open/close pages, headed browsing), `FormInspector` (DOM → `FormModel`), `FormFiller` (`FormModel` + `AnswerBook` → `FillPlan` → `FillReport`).
- Playwright (Chromium) is the first `BrowserProvider`. Playwright types never leave `infrastructure/browser/playwright/`; the domain sees only `BrowserPage` (an opaque handle with a restricted capability set, §13.5).
- ATS-specific `FormFiller` adapters (`form_fillers/greenhouse`, etc.) are added **only** when the generic filler demonstrably fails on that ATS (documented by a failing fixture test).

### 13.2 Form model

```python
@dataclass(frozen=True, slots=True)
class FormField:
    field_id: str                     # stable per inspection (selector + index)
    kind: Literal["text","email","tel","url","number","date","textarea","select","radio_group","checkbox","file","combobox","unknown"]
    label: str | None                 # resolved label text
    accessible_name: str | None
    name_attr: str | None; id_attr: str | None; autocomplete_attr: str | None
    aria: Mapping[str, str]
    description: str | None           # aria-describedby / helper text
    options: Sequence["FieldOption"]  # for select/radio/checkbox groups
    required: bool
    section_hint: str | None          # fieldset legend / heading
    validation_message: str | None
    classification: "FieldClassification"   # §13.3
    step_index: int
```

`FormModel` = fields + steps (multi-step detection) + detected controls (`submit_controls`, `next_controls`, `back_controls`) + `is_final_step: bool | None`.

### 13.3 Field recognition and classification

Signals combined (weighted): `autocomplete` attribute (strongest), `type`, `name`/`id`, associated `<label>`/`aria-label`/`aria-labelledby`, placeholder, nearby text/legend, ARIA role, option sets. Output `FieldClassification(class, confidence, evidence[])`.

Classes and policy:

| Class group | Examples | Policy |
|---|---|---|
| `fillable_profile` | first/last/full name, email, phone, address parts, LinkedIn/GitHub/portfolio URLs, current employer/title, education fields, resume/cover-letter **file upload**, years of experience (if profile has it) | Fill when `confidence ≥ 0.85` **and** the answer book has a value. |
| `user_supplied_answer` | work authorization, sponsorship need, notice period, start date, desired salary, relocation | Fill **only** if the user explicitly stored that exact answer in the answer book; never infer. |
| `blocked_demographic` | gender, race/ethnicity, veteran status, disability, sexual orientation, age/birth date where voluntary self-ID, religion | **Never fill.** Leave blank (including "decline to answer" choices). |
| `blocked_legal` | "I certify/agree/acknowledge", terms/privacy consent, background-check authorization, non-compete/arbitration acknowledgments, e-signature, "information is true" attestations, marketing opt-ins | **Never fill or tick.** |
| `blocked_sensitive` | SSN/national ID, passport, bank details, DOB (when not clearly "voluntary start date" etc.), passwords, security questions | **Never fill.** |
| `free_text_unknown` | essay/"Why us?"/open questions | Leave blank unless the user provided a saved reusable snippet and explicitly maps it; no generation in MVP. |
| `unknown` | unrecognized | Leave blank. Reported to the user. |

Unknown or low-confidence fields remain blank and are listed in the `FillReport` as `skipped` with reason.

### 13.4 Fill execution

1. `browser.open_job` opens the application URL in a **headed** browser window the user can see and control. No credentials entered by the app; if a login/CAPTCHA/anti-bot wall appears, the app stops and tells the user to proceed manually.
2. `browser.inspect_form` produces the `FormModel` for the current step (and re-inspects on DOM mutation / step change).
3. `FormFiller.plan` creates a `FillPlan` of `(field, value, confidence, source_in_profile)` entries; the UI shows a **review panel** (what will be filled, what is skipped/blocked and why).
4. User confirms → `browser.autofill` applies the plan using only fill/select/check/upload primitives, with human-like but minimal delays; verifies each value was accepted (read-back), captures validation messages, and reports.
5. The browser stays open. **The user reviews and submits manually.** Closing is the user's action.
6. Dynamic controls (comboboxes with async options, custom dropdowns, date pickers) are handled via accessible-role interactions; if a control can't be reliably operated, leave blank and report.

### 13.5 Critical safety requirement: never submit (defense in depth)

The application **MUST NEVER** submit a job application, automatically or semi-automatically. This is **not configurable**.

Never:

- click Submit / Apply (when it submits) / Finish / Send / Confirm / Complete;
- trigger `form.submit()`, `requestSubmit()`, or dispatch submit events;
- press **Enter** in fields (implicit submission) or use keyboard shortcuts that could submit;
- invoke submission APIs or replay form POSTs;
- tick legal attestations/consents;
- guess unknown answers;
- answer demographic questions.

Implementation requirements (all MUST be implemented and tested; any one alone is insufficient):

1. **Capability-restricted page handle.** `BrowserPage` exposes only: `goto`, `snapshot_dom`, `fill_text`, `select_option`, `set_checked`, `choose_radio`, `upload_file`, `read_value`, `read_validation`, `screenshot`, and (flag-gated) `click_step_control`. It exposes **no** generic `click`, `press`, `evaluate`, or `dispatch_event`.
2. **Click guard (only `click_step_control`, default disabled):** allowed only when `features.autofill.allow_step_navigation=true` AND the control was classified `step_next` with confidence ≥ 0.90 AND is not `type=submit` AND not matching the submit lexicon AND `FormModel.is_final_step` is `False` (not `None`). Otherwise raises `SubmissionGuardError`.
3. **Submit lexicon** (case-insensitive, multi-language, configurable list): submit, apply, apply now, send application, finish, complete application, confirm, done, review and submit, etc. Matching is against text, `value`, `aria-label`, `title`, and `id/name`.
4. **Network guard:** the Playwright context installs a request interceptor that **aborts** (and logs) `POST/PUT/PATCH` navigations/requests whose URL or body shape matches known application-submission endpoints (per-ATS pattern table) or any form-encoded/multipart main-document submission originating from the page's application `<form>` element. Resume upload pre-signed/temporary upload requests that are *not* submissions are allowed via an explicit allow-list per ATS; unknown uploads are allowed only if the page handle's `upload_file` initiated the file selection and the request is to a different host path pattern than the form action. Interceptor decisions are logged. The interceptor is armed when the session's page opens and re-armed by every fill; it is never time-boxed, because a page may post seconds after a fill. The single way to disarm it is an explicit user *handoff* (`browser.handoff`, §13.4.5), which submits nothing itself (ADR 0008).
5. **Keyboard guard:** the provider rejects any `press`/`type` with `Enter`, `NumpadEnter`, or key chords; text is set via value-setting + `input`/`change` events, not simulated typing of newline characters. Values containing `\n` into single-line inputs are rejected.
6. **Static scan test:** a CI test greps the infrastructure/browser and form-filler packages for forbidden API usage (`.click(`, `.press(`, `.submit`, `requestSubmit`, `dispatchEvent`, `page.evaluate` outside the allowlisted DOM-snapshot module) and fails the build on violations.
7. **Safety fixtures:** a local fixture application site (several ATS-like layouts, multi-step, with tempting "Next"/"Submit" buttons, honeypot hidden fields, consent checkboxes, EEO sections) used by safety tests. The fixture server counts submissions; the safety suite asserts **zero** submission requests, **zero** checked consent boxes, **zero** filled demographic fields, across all scenarios, including adversarial labels.
8. **Fail-closed:** any ambiguity (guard exception, classifier crash, unknown control) results in doing nothing for that element.

### 13.6 Multi-step forms

Default behavior: fill the **current step only**, then wait. A `MutationObserver`/navigation watcher detects when the user advances; the UI offers **"Fill this step"** each time. Only with `allow_step_navigation=true` (off by default) may the app click a *high-confidence, non-final-step "Next"* control as described above.

### 13.7 Anti-bot, authentication, and ToS

- The browser is used for the user's own application; it is not used for mass crawling of protected sites. Rendered-DOM extraction (§6.5) is subject to the same crawl policies and stops at challenges.
- No CAPTCHA solving, stealth plugins, fingerprint spoofing, or credential handling by the app.

## 14. Database design (SQLite)

### 14.1 Database settings

On every connection:

```sql
PRAGMA busy_timeout = 30000;   -- a writer waits for the lock instead of failing
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = NORMAL;
PRAGMA temp_store = MEMORY;
PRAGMA cache_size = -20000;       -- ~20 MB
```

- **Single writer** connection (serialized via an async queue) + a small pool of read connections (default 4).
- Migrations: forward-only numbered SQL files `NNNN_description.sql` in `infrastructure/persistence/sqlite/migrations/`, tracked in `schema_migrations(version, name, applied_at, checksum)`. Each runs in a transaction. Before migrating an existing DB, create a timestamped backup (`.bak` via SQLite online backup API). Migration tests apply all migrations to an empty DB and to fixtures of prior versions.
- Never `DROP`/`DELETE` historical tables in a migration; deprecate with new columns/tables.
- Use `STRICT` tables where supported (SQLite ≥ 3.37) and `CHECK` constraints for enums.
- Delete policy: user-initiated "delete my data" is the only path that removes history; normal operation is append-only for history tables. Soft-state columns (`archived_at`) are used for user-visible removal of sources/profiles.

### 14.2 Schema (normative DDL; types abbreviated where obvious)

> IDs are `TEXT PRIMARY KEY` ULIDs. Timestamps `TEXT` (UTC ISO-8601). `_json` columns hold JSON. Only key tables show every column; others show the required minimum and MAY add columns via migrations.

## 15. Worker architecture and IPC contract

### 15.1 Transport

- **Between Rust and Python:** the worker is a Tauri **sidecar**; communication via stdin/stdout using **NDJSON** (one UTF-8 JSON object per line; max line 8 MB; larger payloads transferred by reference, e.g. a temp file path in the app data dir). stderr is for structured logs only (JSON lines), collected by Rust into the log file.
- **Between webview and Rust:** a single generic Tauri command `worker_request({method, params, request_id?}) → result` and an event channel `worker://event` forwarding worker events. Rust enforces an **allowlist of method names** (generated from the schema registry), validates envelope shape, enforces size limits, and does not interpret payloads.
- The frontend wraps these in a typed `WorkerClient` generated from JSON Schemas (Pydantic → JSON Schema → TypeScript via `json-schema-to-typescript`). A CI check fails if generated types are stale.

### 15.2 Versioning

- `protocol_version` (integer, currently `1`) is negotiated on startup: worker emits `worker.ready {protocol_versions:[1], app_version, schema_version}`; UI replies with `system.hello {protocol_version:1, ui_version}`. Mismatch → blocking UI error with upgrade guidance.
- Compatible changes (new optional fields, new methods/events) do not bump the version. Breaking changes require `v2` methods side-by-side for one release.
- Each method has `params_schema` and `result_schema` ids (`jobs.search@1`).
- The DB `schema_version` is reported in `system.health`; the UI refuses to run against a newer DB schema than it understands.

### 15.3 Message envelopes

```jsonc
// Request (UI → worker)
{ "v": 1, "type": "request", "id": "01J...", "method": "jobs.search",
  "params": { ... }, "meta": { "deadline_ms": 30000, "idempotency_key": "optional" } }

// Success response
{ "v": 1, "type": "response", "id": "01J...", "ok": true, "result": { ... } }

// Error response
{ "v": 1, "type": "response", "id": "01J...", "ok": false,
  "error": { "code": "validation.invalid_params", "message": "…", "retryable": false, "details": { ... } } }

// Event (worker → UI), optionally tied to a long-running task
{ "v": 1, "type": "event", "topic": "discovery.progress", "task_id": "01J...", "seq": 42,
  "ts": "2026-03-01T14:05:09Z", "data": { ... } }
```

- **Request IDs** are unique per UI session; responses match on `id`. The worker processes requests concurrently (bounded; per-method concurrency limits), not necessarily in order.
- **Long-running operations** return immediately: `result: { "task_id": "…" }`; progress and completion arrive as events: `task.progress`, `task.completed`, `task.failed`, `task.cancelled` plus domain-specific topics.
- **Cancellation:** `tasks.cancel {task_id}` → cooperative cancellation; the worker emits `task.cancelled` once cleanup finishes. Cancelling an unknown/finished task is a no-op success.
- **Backpressure:** events are coalesced (progress at most 5/s per task); the worker drops intermediate progress when the UI lags, never terminal events.
- **Idempotency:** mutating methods accept `idempotency_key`; duplicates within 10 minutes return the original result.
- **Error codes** (stable, namespaced): `validation.invalid_params`, `not_found`, `conflict`, `permission.denied`, `unsupported.version`, `task.cancelled`, `task.timeout`, `plugin.unavailable`, `plugin.circuit_open`, `network.offline`, `robots.disallowed`, `storage.locked`, `storage.migration_required`, `internal.unexpected` (with `incident_id` logged).
- **Security:** methods that can open files accept only paths returned by Tauri file dialogs (validated server-side to be inside user-selected files); no arbitrary-shell or arbitrary-URL fetch methods exist.

### 15.6 Worker internals

- **Dispatcher:** method name → handler registry (`worker/ipc/handlers/*`), each handler validates params via Pydantic, calls an application use case, maps domain errors to IPC errors. No business logic in handlers.
- **Task runner:** priority queue + asyncio workers; CPU-bound steps (fingerprinting, TF-IDF, PDF parsing) run in a bounded `ProcessPoolExecutor`/thread pool; configurable limits; tasks persisted to `background_tasks`; on restart, `running` tasks become `interrupted` and are optionally resumed (discovery/analysis are resumable by design via incremental diffs).
- **Scheduler:** wakes at the earliest `next_run_at`, respects global concurrency, quiet hours (optional), battery/metered-connection guard (optional), and "pause all" toggle. Jittered.
- **Single-writer discipline:** all writes go through UoW on the writer connection; long computations happen outside transactions; transactions per job (bounded size).
- **Logging:** structured JSON logs with fields `ts, level, component, event, task_id, plugin_id, url_host, duration_ms, error_code`; **never** log resume text, personal data, or full job descriptions; log rotation (10 files × 5 MB); log redaction filter with tests.

## 17. Performance, reliability, and observability

### 17.1 Budgets (targets, verified by benchmark tests on reference hardware: 4-core laptop, SSD)

| Metric | Target |
|---|---|
| Cold start to interactive UI | ≤ 3 s (worker ready ≤ 2 s) |
| Idle CPU (no tasks) | < 1% |
| Idle memory (UI + worker, no browser) | ≤ 350 MB total |
| Memory during crawl (no browser) | ≤ 700 MB |
| `jobs.search` over 100k jobs (FTS + filters, first page) | p95 ≤ 150 ms |
| `jobs.get` | p95 ≤ 50 ms |
| Ingest throughput | ≥ 20 jobs/s persisted after fetch (CPU-bound path), excluding network |
| UI list scroll | 60 fps with 10k rows (virtualized) |
| Database size | ~ 1 GB per 200k jobs with snapshots (tracked; compaction §17.4) |

### 17.2 Concurrency and resource control

- Asyncio throughout the worker; global concurrency cap (default 8 requests), per-origin cap 2, per-origin token bucket (1 req/s default), per-source run budgets (requests, bytes, wall-time).
- One shared crawl gate (`crawl.global_concurrency`) bounds **concurrent source crawls**, whether they come from a per-source schedule or from the automatic discovery pass. The pass additionally caps how many sources it registers and crawls (`discovery.max_*_per_run`), so background work never starves user-initiated requests or the UI.
- Background priorities: user-initiated (`1`) > on-demand verify (`2`) > discovery (`5`) > analytics/maintenance (`8`). Lower-priority tasks yield (cooperative `await sleep(0)` checkpoints) and pause when the UI window is focused and heavy interaction is detected (optional "quiet mode").
- Playwright is started lazily, limited to 1 browser with ≤ 2 pages for extraction, closed after idle timeout (60 s).
- CPU-bound work (fingerprinting, TF-IDF, parsing) offloaded to a bounded executor; large batches chunked.

### 17.3 Incremental processing and caching

- **Content hashing:** every fetched body and normalized description gets a stable hash. If unchanged since the last snapshot, skip normalization, fingerprinting, keyword extraction, matching, and signal recomputation (record only a `seen` observation).
- **Conditional HTTP** via ETag/Last-Modified; coalesced duplicate requests; per-origin cached metadata (robots, ETags, pagination hints).
- **Listing diff:** only fetch details for new refs or refs whose `updated_at_hint` changed.
- **Input-hash invalidation** for matching and risk evaluation (`input_hash` = hash of job snapshot id, profile hash, weights, model version). Recompute only when changed.
- Do not re-download the same job description without reason (a "no refetch within N hours unless forced" guard, default 6 h).

### 17.4 Reliability

- Retry policies per §6.6; per-source backoff; circuit breakers per plugin (§4.6).
- Crash safety: transactions per job; WAL; on worker restart, interrupted tasks are reconciled; orphaned temp files cleaned.
- Database integrity check (`PRAGMA quick_check`) on startup (full check on demand); automatic pre-migration backups; scheduled local backup (default weekly, keep 4) to the app data directory; manual export/import (§15.4).
- Storage management: snapshots of unchanged content are not duplicated (content-hash dedupe: new `seen` observation only). Optional compaction of `description_html` for jobs removed > 12 months while preserving `description_text`, fingerprints, and signals. Compaction is user-visible and opt-in.
- Clear error reporting: errors have stable codes, user-readable messages, remediation hints, and link to the relevant log/`crawl_events` entries; a "Copy diagnostics" action excludes personal data.

### 17.5 Observability (local only)

- Structured JSON logging (§15.6) with component/plugin/task correlation IDs.
- `system.health` aggregates: DB status, plugin health/circuit state, last crawl per source, queue depth, memory.
- In-app diagnostics page: recent errors, slow queries (> 200 ms logged with query name, not parameters), task history.
- No remote telemetry or crash reporting. Optional "export diagnostics bundle" is user-initiated and redacted (§18).

## 18. Security and privacy

### 18.1 Threat model (summary)

| Asset | Threats | Mitigations |
|---|---|---|
| Resume/PII/answer book | Exfiltration via network, logs, crash dumps, malicious page content | No outbound user-data traffic (CI test with network-denied mode and request logging assertions); logging redaction; local-only storage; optional OS-keychain-based encryption (see 18.3) |
| Local DB | Other local users/processes | App data dir with user-only permissions (0700/ACL); optional SQLCipher (ADR-0009, off by default) |
| Webview | XSS from untrusted job HTML | Sanitize all job HTML (allowlist sanitizer, strip scripts/styles/forms/iframes/event handlers/`javascript:` URLs; links open in the system browser with `rel=noopener`); strict CSP (`default-src 'self'`; no remote scripts; no inline scripts); render descriptions in a sandboxed container |
| IPC | Malicious/compromised webview calling dangerous methods | Method allowlist in Rust; Tauri capabilities minimized; schema validation in Rust and Python; no file-path or URL methods that accept arbitrary strings without dialog provenance; no shell exec |
| Crawler | SSRF to local network, huge responses, zip bombs | Block private/loopback/link-local IP ranges and non-http(s) schemes for crawled URLs (with explicit per-source override disabled by default); size/time caps; decompression limits; redirect cap (5) with re-validation of each hop |
| Browser automation | Auto-submission, credential capture | §13.5; dedicated browser profile in `browser-profile/` (not the user's main profile); no password autofill; the app never reads cookies |
| Supply chain | Malicious dependencies | Pinned lockfiles (`uv.lock`/`pip-tools`, `pnpm-lock`, `Cargo.lock`), `pip-audit`/`npm audit`/`cargo audit` in CI, minimal dependencies, reproducible sidecar builds, code-signed installers |
| Plugin code | Third-party code | Not supported in MVP (`external_plugins=false`); builtin plugins declare network hosts, enforced by `PolicyHttpClient` (connector can only call its declared hosts) |

### 18.2 Privacy commitments (enforced and tested)

1. No accounts, analytics, or telemetry.
2. Resume text and profile data never appear in outbound requests, logs, or URLs.
3. Optional network features are listed in Settings → Privacy with exactly what is sent (e.g. search queries for `discovery.search_engine`).
4. `delete-my-data` removes DB, resumes, caches, logs, and browser profile after confirmation.
5. Data export is a user-initiated single archive; the user chooses whether to include resumes.

### 18.3 Optional hardening (post-MVP unless stated)

- At-rest encryption: SQLCipher or OS-level disk encryption guidance; resumes encrypted with a key held in the OS keychain (via Tauri plugin). Documented as optional because it affects performance and recovery.
- Security review is a Milestone 11 deliverable: threat model update, dependency audit, IPC fuzzing, HTML-sanitizer tests with known XSS corpora, crawler SSRF tests.

## 19. Testing strategy

### 19.1 Layout and tooling

```text
tests/
  unit/          domain + application, pure, fast (no I/O); property-based where useful (hypothesis)
  contract/      reusable contract suites run against every adapter
  integration/   SQLite, IPC, crawl orchestration, end-to-end use cases with fakes
  safety/        autofill safety, crawl-policy safety, privacy/no-network
  swapability/   §4.8
  fixtures/      recorded HTTP responses (per ATS), HTML pages, resume files, fixture application site
  support/       fakes: FakeClock, FakeHttpClient, InMemoryUnitOfWork, FakeBrowserProvider, ToyAtsConnector...
frontend/src/**/__tests__   Vitest + Testing Library; Playwright e2e smoke on the built app
src-tauri/ tests            cargo tests for supervisor and allowlist
```

- CI matrix: Windows, macOS, Linux. Coverage gates: domain ≥ 90% line coverage, application ≥ 85%, adapters ≥ 75%; mutation testing (mutmut) on risk aggregation, dedup decisions, and suppression logic (non-blocking, tracked).
- **Determinism:** all time via `FakeClock`; ULID generator seeded; no real network (socket-blocking fixture by default); no sleeps.
- **HTTP fixtures** are recorded once from live endpoints (script in `scripts/record_fixtures`), scrubbed, and committed; connector tests assert parsing against them. A separate non-blocking "live smoke" job (manual/nightly) detects upstream endpoint drift.

### 19.2 Unit tests (required coverage)

Normalization (titles, locations, salary, URL canonicalization, HTML-to-text) · Deduplication and fingerprints · Job identity resolution decision table (every row, plus guards) · Repost detection · Application cooldown and suppression policies (including expiry, restore, "save/dismiss don't start cooldown") · Matching strategies and aggregation (including unavailable dimensions) · Hard filters (unknown handling) · Keyword extraction/normalization (disambiguation cases like `Go`, `R`, `C#`) · Each posting signal provider (golden fixtures, missing-data behavior) · Risk aggregation formulas (worked examples from §9.4) · Confidence calculation · Classification thresholds (boundary values) · Company-level tiering and Wilson intervals.

### 19.3 Contract tests (every adapter)

| Suite | Applies to | Key assertions |
|---|---|---|
| `ConnectorContractSuite` | every ATS connector | list/fetch shape, pagination, empty, malformed item tolerance, 404 tenant, 429 + `Retry-After`, cancellation, only declared hosts contacted, no cookies, provenance populated |
| `DiscoveryProviderContract` | every provider | emits valid `DiscoveredSource`, dedupes, respects cancel, no network if declared offline |
| `ExtractionStrategyContract` | every strategy | `can_attempt` purity, returns Result (never raises), field confidences within range, deterministic for fixture |
| `RepositoryContract` (per repository) | SQLite + in-memory | CRUD, uniqueness, append-only enforcement, ordering/pagination, concurrency |
| `BrowserProviderContract` | Playwright + Fake | open/close lifecycle, restricted page handle (no click/press/evaluate exposed), screenshot, timeouts |
| `PostingSignalProviderContract` | every provider | pure/deterministic, missing → `status=missing` with `risk_contribution=None`, confidence ∈ [0,1], evidence present when available |
| `ResumeParserContract` | every parser | text extraction on fixture resumes, graceful failure on corrupted/encrypted/empty, never mutates original |
| `ScoringModelContract` / `MatchingStrategyContract` | every model/strategy | scores ∈ [0,1], unavailable handling, explanation present, deterministic |
| `HttpClientContract` | httpx + fake | timeouts, redirects cap, size cap, error mapping to `PortError` |

### 19.4 Integration tests

SQLite persistence & migrations (including upgrade from each prior schema fixture) · Worker IPC end-to-end (spawn worker subprocess; request/response/event/cancel; protocol negotiation; invalid params; large payload by reference) · Crawl orchestration (fixture site: listing → fetch → extract → persist; not-seen/removal logic; failing source isolation; resumption after interruption) · Extraction fallback chain (each strategy failing in turn → ends in partial record with provenance) · Historical observations (append-only, reproducible timelines) · Application tracking and suppression flow (apply → repost arrives → suppressed → expiry → reappears) · Ghost-job risk history (assessments reference exact signal sets; reproducibility golden test).

### 19.5 Safety tests (CI-blocking)

1. **No submission:** against the fixture application site (§13.5.7), run autofill in all scenarios; assert zero submission requests, zero clicks on submit-lexicon controls, zero Enter keypresses; static scan test for forbidden APIs; allowlist test that `browser.submit`/`browser.click` methods do not exist.
2. **No automatic legal attestations:** consent/certification checkboxes remain unchecked; signature fields blank.
3. **No automatic demographic answers:** EEO/self-ID fields remain blank, including "decline to answer" options.
4. **Unknown fields blank:** unclassified or low-confidence fields untouched.
5. **No CAPTCHA bypass:** fixture challenge page → crawl records `blocked`, backs off, makes no further attempts in the run, never invokes solver code (no such code exists; dependency scan for stealth/solver libraries).
6. **No access-control circumvention:** 401/403/login-redirect → `auth_required`, no credential entry, no retry with altered headers; robots-disallowed URLs never fetched (assert via fake HTTP request log).
7. **Privacy:** network-denied run of resume import, matching, application tracking passes; log scanner confirms no resume text/PII in logs.
8. **SSRF:** crawl of `http://127.0.0.1`, `169.254.169.254`, `file://` rejected.

### 19.6 Repost tests

Same job with new URL → attach alias, `reposted_identical` · Same job with new ATS ID → same · Slightly changed description (below material threshold) → repost, `material=false` · Material change → `materially_updated` · Reset posting date with identical content → `posted_date_reset=true` · Similar but distinct position (different location/team/req ID) → `similar_distinct`, not merged · Multiple simultaneous openings of same title with different locations → remain separate · Ambiguous tie → `similar_distinct` with `ambiguous=true` · Manual merge/unmerge persists and is never reversed by automation.

### 19.7 Ghost-job tests

- Old posting alone does not imply high risk (only `posting_age` available → class `needs_verification`, risk ≤ 0.30).
- Explicitly closed application endpoint increases risk (and forms a strong signal → `likely_inactive` with confidence ≥ 0.70).
- Missing evidence never raises risk: removing any signal's data yields the same or lower evidence mass, never higher risk than with it replaced by `missing` vs. `0`; property test: marking a signal `missing` never increases `risk` beyond the prior-shrunk value of the remaining signals.
- Multiple weak signals combine cautiously (3 signals at `r=0.5, c=0.3` do not reach `likely_inactive`).
- Strong signals affect risk appropriately (floor rule).
- Confidence remains distinct from risk (high risk/low confidence case yields `needs_verification` or `likely_stale` per table, never `likely_inactive`).
- Company-level conclusions require sufficient samples (tier gating; no labels at insufficient/limited tiers).
- Historical observations persist (re-evaluation appends; nothing overwritten; attempted UPDATE on immutable tables fails).
- Risk scores reproducible from stored signals + model version + config hash.
- Transient endpoint failures (single timeout) are *missing*, two consecutive → weak signal; `blocked`/`auth_required` never count as negative evidence.
- Classification threshold boundary tests (0.30/0.50/0.75 × confidence 0.30/0.35/0.40/0.50).

### 19.8 Outcome tests

Outcomes tracked and linked to applications · Response/interview/rejection/no-response rates computed correctly (golden dataset) with Wilson intervals · Buckets with `n < 5` hidden · `no_response` is never transformed into a risk signal automatically · UI/IPC copy scan: no causal language ("proves", "caused", "confirms ghost") · Calibration proposals require ≥ 30 outcomes and explicit user acceptance.

### 19.9 Frontend tests

Component tests for badges/explanation panels (accessible names, no bare scores), table virtualization, filters, autofill review panel (blocked/skipped labels, no "Submit" wording), IPC client typing (generated types in sync), error/empty states. E2E smoke (Playwright against the built app with a worker running on fixtures): add source → discover → view job → save → mark applied → see suppression.

### 19.10 Funnel tests

Tier assignment respects profile + hard filters (golden profile/fixture boards) · a tier never crawls more often than its interval · tier reassignment after profile changes is explainable and evented · harvested posting URLs are verified with at most one fetch before extraction · harvested-only postings never create `not_seen` observations and never mark a job `removed` · identity resolution dedupes a harvested posting against a full listing of the same posting · funnel passes never exceed the pass caps or the global crawl gate · disabling `discovery.funnel_enabled` restores plain due-based crawling.

## 21. Implementation roadmap

**Rules:** implement one milestone at a time; each milestone ends with passing tests, updated docs, and a short report. Do not pre-implement later milestones (stubs behind ports are fine only where Milestone 0 requires fakes).

### Milestone 0 — Architecture and desktop foundation

**Deliverables:** Tauri 2 shell; React/TS app with routed empty screens and a Settings/Diagnostics page; Python worker sidecar with NDJSON IPC, handshake, health, tasks, cancellation scaffolding; Rust supervisor + method allowlist; SQLite init, WAL, migration framework (migration 0001 = infrastructure tables + core skeleton), backup-before-migrate; domain/application/infrastructure layout with import-linter contracts; all ports from §4.2 defined; composition root with typed `AppConfig` and feature flags; `PluginRegistry` with isolation shim and circuit breaker; structured logging with redaction; fakes (`FakeClock`, `FakeHttpClient`, `InMemoryUnitOfWork`, `FakeBrowserProvider`, `ToyAtsConnector`, `ToySignalProvider`, `ConstantScoringModel`); contract test base classes; swapability tests S1–S9 (those whose subjects exist as fakes); schema → TS type generation; CI for all three OSes.
**Exit criteria:** `system.hello/health` round-trip from UI; worker crash/restart handled; swapability + boundary tests green; no crawling/ATS/resume/matching/ghost/browser code.

### Milestone 1 — Discovery framework and initial connectors

**Exit:** connector contract suites green; incremental crawl skips unchanged jobs; failing source isolated; not-seen/removal logic tested.

### Milestone 2 — Universal extraction

### Milestone 3 — Search and job history

Search profiles, hard filters, search results with FTS; fingerprints; deduplication and identity resolution; repost detection and events; snapshots/material-change logic; historical observation views; manual merge/unmerge; "Seen/Duplicates" view.

**Exit:** all repost tests (§19.6) green; no over-merging of simultaneous openings.

### Milestone 4 — Automatic discovery and daily scheduling

**Deliverables:** `discovery.auto_discover` pass that runs all enabled discovery providers on a daily schedule without user input; **seed-free discovery of career sites** via `discovery.web_index` (public web URL index, rotating `(ATS host, bucket)` cursor persisted in `app_settings`), so neither a bundled seed list nor user-added sources are required; the seed file demoted to an offline bootstrap; auto-registration of newly discovered career sites as `SourceConfig` rows with the configured default schedule; per-pass budgets for registration and crawling (`discovery.max_new_sources_per_run`, `discovery.max_crawl_sources_per_run`) plus a shared global crawl concurrency gate; due-based crawl selection (never crawled, or own interval elapsed) so a pass stays bounded as sources accumulate; persistent per-source scheduler with cron/interval schedules that survives worker restarts; `discovery.auto_discover` IPC method; daily crawl trigger that runs the due sources and records `crawl.completed`/`crawl.failed` events; search profiles (from M3) begin receiving newly discovered jobs automatically.
The crux of this whole desktop app is that jobs find the user, not that the user needs to search for jobs. The best jobs available at a certain time need to be found for a user to find and apply to a job and maximize their chances of getting a job that they are satisfied with. We want to maximize success and satisfaction and limit manual actions and automate as much as possible to make job searching far less mentally taxing.
As shipped, a pass walks `discovery.cursor_step` (default 12) index slices in parallel, crawls the due sources concurrently through the shared gate, and the web-index provider dedupes tenants across hosts within a pass (see §6.2 for the shipped behavior and budgets).

**Exit:** with the bootstrap seed file empty, a pass still discovers and registers career sites on fixture index data in bounded time; the rotation cursor and the cadence both survive a worker restart; no user input required to populate sources; a pass never exceeds its registration/crawl budgets or the global crawl gate; jobs flow into search profiles with hard filters applied.

## 22. Development practices and ADR process

1. Read this entire specification before starting any milestone.
2. Implement only the requested milestone; do not prematurely implement future milestones.
3. Write tests alongside code; a feature without tests is not done.
4. Keep modules small and cohesive; prefer composition over inheritance.
5. Use typed interfaces (mypy strict in `domain/` and `application/`; TypeScript `strict`).
6. Document non-obvious decisions in `docs/adr/NNNN-title.md` (context, options, decision, consequences). Mandatory ADRs: PDF library licensing (ADR-0003), SQLCipher decision (ADR-0009), auto-update (ADR-0012), embedding model selection when enabled.
7. Avoid unnecessary dependencies; justify each new dependency in the PR description (size, license, maintenance, alternatives).
8. No hard-coded configuration; use typed `AppConfig`.
9. Preserve historical data; never add destructive migrations.
10. Always use migrations for schema changes; update repository contracts and tests.
11. Keep UI state separate from domain logic; no scoring or policy logic in TypeScript.
12. Keep every external integration replaceable and contract-tested.
13. Prefer simple designs: when an architectural decision is unclear, write down the trade-offs and choose the simplest design that preserves future replaceability.
14. Conventional commits; small PRs per vertical slice; CI must be green (lint, types, unit, contract, boundary, safety).
15. Never weaken a safety test to make a build pass; changes to §13.5 safeguards require an ADR and explicit maintainer approval.
16. Definition of Done per feature: code + unit tests + contract tests (if an adapter) + docs/ADR (if decision) + IPC schema regenerated + UI copy reviewed for cautious language.

## 23. Final acceptance criteria

The completed application MUST satisfy all of the following:

1. Discovers jobs from multiple ATS platforms and ordinary career sites.
2. Attempts generic extraction on unknown ATS platforms; never declares an ATS "unsupported" merely for lack of an API.
3. Preserves partial records with provenance and confidence when extraction is incomplete.
4. Avoids repeatedly presenting the same job as new (aliases, snapshots, `seen` observations).
5. Recognizes reposts even when URLs, source IDs, or posting dates change, and distinguishes the five repost classes with evidence.
6. Tracks companies and application history durably.
7. Suppresses recently applied-to roles per configurable policy; only actual applications trigger cooldowns; users can restore any job; nothing is deleted.
8. Keeps unrelated roles at the same company visible by default.
9. Identifies potentially stale or inactive postings using multiple independent signals.
10. Explains every ghost-risk assessment, deprioritization, suppression, and ranking decision with evidence.
11. Keeps risk and confidence separate; missing data is never negative evidence.
12. Maintains append-only historical observations, signals, and assessments; assessments are reproducible from model version + config.
13. Produces company-level hiring intelligence only with adequate samples and cautious language.
14. Improves analysis using locally recorded application outcomes without claiming causation.
15. Ranks jobs by candidate fit and (optionally, user-controlled) posting credibility, with fit and credibility displayed separately.
16. Parses resumes locally (PDF/DOCX/TXT), preserves originals, supports versions and manual correction.
17. Analyzes skill prevalence by distinct jobs and shows resume coverage without fabricating experience.
18. Autofills application forms safely and **never submits applications**, accepts legal attestations, guesses unknown answers, or answers demographic questions.
19. Operates locally without mandatory cloud services, accounts, or paid API keys; optional external features are disclosed and off by default.
20. Any subsystem (HTTP client, repositories, browser, connectors, extraction strategies, scoring models, signal providers) can be replaced without rewriting the application, proven by CI swapability tests.
21. Favors trustworthy, explainable results over aggressive automation or inflated job counts.
